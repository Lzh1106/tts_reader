# v1.21.53 改动说明 —— EPUB / TXT 朗读的句子跟随

> 版本：**1.21.53+114** ｜ 日期：2026-10-16 ｜ 基线：v1.21.52+113
> 任务：修「句子跟随滚动不稳定（偶发不居中 / 位置不对）」+「重回阅读页有概率不在朗读位置」

---

## 一、结论先行

两个现象都不是"滚动没跑"，而是**判据本身算错了**：

| 现象 | 根因 | 性质 |
| --- | --- | --- |
| 句子跟随不稳定、偶发不居中 / 位置不对 | 句子纵向位置**靠估算**，只数 `\n`；中文段落全是**软换行**，于是段内每句的「句顶」**恒等于段顶** | 判据错误 |
| 重回阅读页不在朗读位置 | ①「视图位置」取**视口最顶端那一段**，而跟随按设计把朗读句放 38% → 记下的位置系统性落后；②进入定位只拉**段落**、且只做一次，段比屏高时「段进视野」≠「那句进视野」 | 判据错误 + 缺一步 |

**两个都不是"日志相邻性凑出来的因果"** —— 见第三节的负向自检：把判据改回去，
对应用例立刻变红，且日志复现出真机那个数。

## 二、逐处改动（diff 级）

只动了一个源文件：`lib/pages/reader_page.dart`（另加 `pubspec.yaml` 版本号、`CHANGELOG.md`）。

### 2.1 新增：实测句子的真实渲染盒

**新增** `_measureSentenceInParagraph(blockIndex, chapter, paragraph, sentence)`
与 `_findRenderParagraph(root)`。

* 原理：EPUB 段落是 `Text.rich`，每个句子本来就是**独立的 `TextSpan`**
  （`_ParagraphViewState._span`），字符区间由 `_onSentenceSpans` 上报。
  于是可以用 `RenderParagraph.getBoxesForSelection(TextSelection(start, end))`
  拿到**那一句真实的渲染盒**（跨行时取所有盒子的并集上下沿）。
* 为什么原来没这么干：旧注释写着"精确值要 TextPainter 重新排版，代价高且没必要
  —— 这里只用来分档"。**这个判断是错的**：不需要重新排版，段落本来就已经排好了，
  `getBoxesForSelection` 只是查询已有排版结果。
* 量不到时（段落还没排版）返回 null，调用方**退回估算** —— 两条路都保留，
  否则段落没上屏时跟随会整条失效。

### 2.2 改：`_readingGeometry` → 抽出 `_geometryForCursor`

* `_readingGeometry()` 仍从 `_tts.highlightCursor` 取游标（日常跟随用）；
* **新增** `_geometryForCursor(cursor)`，游标由调用方给。
* 为什么必须拆：`TtsManager.highlightCursor` 只在
  `_speaking && !_oneShot` 时非空 —— **没朗读时恒为 null**。
  而「重回阅读页」恰恰是没在朗读的场景，于是进入定位那条链一个几何都量不到。
  （真机日志表现：`[进入定位结束] 轮次用尽`，而 `[进入定位校验]` 一条都没有。）
* 口径统一为**句心**（不是句顶）：与滚动目标、与 PDF 的
  `bounds.center.dy` 一致，避免"判据看句心、滚动按句顶"。

### 2.3 改：`_followSentence` 按句心对齐

* 原来：`sentenceOffset = 显式换行数 × 行高`，
  目标 = `段顶 - 视口 × 38%`。
* 现在：优先用实测句心，目标 = `句心 - 视口 × 38%`。
* 兜底仍在：实测拿不到时退回估算（并把估算行的中线当句心近似）。

### 2.4 改：`_rememberVisibleSpot` 朗读中直接取朗读位置

* 新增分支：`_tts.speaking && 同页 && 锚点已建出` → `_lastSpot = 朗读游标`。
* 理由：跟随逻辑**按设计**把朗读句放在视口 38%，所以"视口最顶端那一段"**必然**
  是朗读段**之前**的段落 —— 拿它当视图位置是系统性偏差，不是偶发。
  真机日志：`视图位置=(1,0,0) 朗读位置=(1,2,1)`。
* 只在**同页**时这么做：朗读已跑到别的页（用户手动翻走了）时，
  仍按用户实际停留处记，否则会把用户翻到的位置写丢。

### 2.5 新增：进入定位的句子级校验与补正

* **新增** `_alignToSentenceAfterLayout(chapter, paragraph, sentence)`，
  在 `_alignTo` 的 `_revealBlock` 之后 `unawaited` 调用。
* 逻辑：最多 8 轮，每轮量「请求恢复那一句」的句心；
  落在视口 5%~85% 内即完成，否则按句心对齐一次再校验。
* 为什么有限轮次：无限重试会和后续的跟随滚动抢同一个 `ScrollController`
  —— 那正是历史上「页面乱抽」的来源（见 `_runRevealChain` 的注释）。
* 对照 PDF：PDF 的 `_revealToPageIndex` 是**逐帧收敛最多 24 帧**，
  本改动是同一思路的有限版本。

### 2.6 观测日志（第一步的产物，保留）

新增 `朗读跟随[...]` 埋点（`_followLog` / `_followGates` / `_anchorProbe`），
覆盖：游标收到 → 决策（含每个"跳过"原因）→ 几何 → 跟随 → 滚动/不滚 → 定位链 → 进入定位。
**这批日志是这次能定位的原因**，故保留（`CrashLog.mark` 走现有落盘通道，零新增依赖）。

### 2.7 明确**没有**改

* **没有**动分句规则 → `DocumentService.parseRevision` **保持 3 不变**
  （本版只改显示跟随，不影响任何解析结果）。
* **没有**改 PDF 阅读页（`features/pdf_reading/`）任何逻辑 —— 它是这次的**参照**。
* **没有**改 PDF 原版式的取词 / 翻页 / 点句。
* **没有**改朗读主循环、打断处理、焦点策略。

### 3.3 负向自检（三项，**都必须变红**）

交接文档第七节第 4 条：负向自检是唯一能证明"用例真的在守这条线"的手段。
为此加了三个**固定为 false** 的自检开关（生产代码永不启用）。

| # | 关掉什么 | 期望 | 实测结果 |
| --- | --- | --- | --- |
| 1 | `_negativeDisableMeasure`（退回估算） | 软换行两条用例红 | ✅ 红：`实测样本=0/11`、`Expected: >0 / Actual: 0`；日志复现旧 bug：`估算(显式换行=0)@252` **连续 11 次不变**、滚动位移 `0.0` |
| 2 | `_negativeDisableReadingSpot`（视图位置退回旧行为） | 重进用例红 | ✅ 红：`重进后 spot=(0,0,0)`（应 `(0,1,8)`），`Expected: <1> / Actual: <0>` |
| 3 | `_negativeSkipEntryAlign`（跳过句子级补正） | 进入定位用例红 | ✅ 红：`占比=157%`、`句心=542.0 / 视口 346` —— 那句在屏幕外 |

**期间发现并修掉的一个"假测试"**（如实记录）：
第 2 条用例最初只断言"句心占比落在 0~1"，负向自检时**它仍然绿** ——
因为旧实现的估算值恒为段顶、看起来"稳定"在 73%。
改成断言**高亮框真的完整落在屏幕内** + **段内位置必须随句推进而变化**之后才变红。
**教训：只断"没崩"不等于断到了现象；负向自检不过就是没测到。**

### 3.4 新增用例（`test/reader_follow_reliability_test.dart`，4 条）

1. `软换行长段落：跟随必须按实测句心对齐，不能拿段顶当句位`
2. `朗读推进：高亮句必须真的在屏幕上（越界即失败）`
3. `重回阅读页（朗读已停）：进入定位必须把那一句拉进视野`
4. `重回阅读页：定位必须落到朗读句（不只是朗读段）`

配套新增测试专用造书器 `makeTallParagraphBook` —— **段内不写 `\n`、
段落明显高于视口**（对齐真机 580px 段 / 483px 视口）。
旧的跟随用例全是短段（段高约 9 行、三段就满屏），
所以**软换行这个 bug 之前一条用例都没抓到**。

## 四、未决 / 已知限制

1. **模拟器 TTS 不稳**：`系统 TTS 超时（30000ms）` 偶发，导致推进速度受限。
   本次结论主要依据每句的**几何与滚动日志**（与 TTS 快慢无关），不受影响。
2. 建议在真机上复核：找一个**中文长段落**的 EPUB，连读几十句看是否稳定居中；
   再「朗读中退出 → 等几十秒 → 重回」，确认落在朗读句上。
3. 观测日志（`朗读跟随[...]`）目前**保留**。它每条都走串行落盘队列，
   量不大（每句 1~3 条）；若将来嫌吵，可整体降级为 `debugPrint`。
