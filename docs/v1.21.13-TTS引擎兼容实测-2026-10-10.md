# v1.21.13 · TTS 引擎兼容性实测报告（跳句 bug 归因取证）

> 本文件是**本地诊断记录**，不进发布包、不 push 到远程（铁律 8）。
> 实测时间：2026-10-10；装置：`emulator-5554`（AVD `tts_test`，Android 14 `sdk_gphone64_x86_64`）。

---

## ⓪ 一句话结论

**「PDF 点句后位置多跳 5~10 句」与 TTS 引擎的兼容性无关。**

那次被判为「假完成」的信号，**不经过引擎**——它是 `SystemTtsEngine.stop()/pause()` 里
**同步**调用 `_completePending()` 造出来的（`system_tts_engine.dart:189 / 199`），
换任何引擎（MultiTTS / Google / 其它）都一样。

引擎兼容性**确实**存在一个坑，但它造成的是**相反的症状**：不设音色时 MultiTTS
**接收 `speak()` 却完全静默**（不回调 `onStart`/`onDone`）→ 读数循环挂到 30s 超时
（`tts_manager.dart:1608-1626`）→ 表现为「不推进 / 朗读超时」，**不是跳句**。

## ① 装置（可复现）

| 环节 | 做法 |
| --- | --- |
| 引擎探针 | 设备上现成的 `com.probe.tts`（TtsProbe，标准 `android.speech.tts` 客户端，日志 tag `TtsProbe`） |
| 驱动 | `adb shell am start -n com.probe.tts/com.probe.tts.ProbeActivity --es engine <包名> [--es voice <音色名>]` |
| 取引擎原始回调 | `adb logcat -s TtsProbe:*`（探针）与 `flutter_tts` 的 `D TTS` 行（App 路径） |
| 语音包状态 | `/sdcard/Android/data/org.nobody.multitts/files/voice`：`bdetts/90013/acoustic` 61 个声学模型 + `licence.dat`/`text.dat` + `avatar` + `config.yaml`，共 895 MB |
| MultiTTS 入库证据 | `sqlite3 /data/data/org.nobody.multitts/databases/speaker 'select count(*) from Speaker;'` → **52**（52 个角色已入库） |

**关键装置事实（本条推翻 §4.107「模拟器没有可用的系统 TTS 引擎」）**：

- MultiTTS 1.8.3（真机 APK）**只有 arm64-v8a 原生库**（73 个 `.so`，`primaryCpuAbi=arm64-v8a`）；
  本模拟器 `abilist=x86_64,arm64-v8a` 且 `ro.dalvik.vm.native.bridge=libndk_translation.so`，
  即它在 **ARM 二进制翻译**下运行 —— **能跑通**（见 ②）。
- `-no-audio` 只影响扬声器输出，**不影响回调链**：合成照常发生，`onStart`/`onDone` 照常回调。
- 需要 `adb root`（google_apis 镜像可用）才能读 MultiTTS 的内部库；`run-as` 对
  `org.nobody.multitts` 无效（非 debuggable）。

## ② 引擎层矩阵（TtsProbe，同一段文本）

| 引擎 | 客户端是否设音色 | INIT | SPEAK | onBeginSynthesis/onStart | 音频字节 | onDone | VERDICT |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `org.nobody.multitts`（MultiTTS 1.8.3） | **否** | 0 OK | 0 | **无** | 无 | **无** | 静默挂住（25s+ 零回调） |
| `org.nobody.multitts` | 是（`bdetts_paimeng`） | 0 OK | 0 | `BEGIN rate=24000 enc=2 ch=1` / `START` | 178526 | 有（读完才回） | **PASS-AUDIO** |
| `com.google.android.tts` | 否 | — | 0 | `BEGIN` / `START` | 178560 | 有 | **PASS-AUDIO** |
| `com.m3tts`（MultiTTS M3，x86_64） | 否 | — | 0 | `START` | 114662 | 有 | **PASS-AUDIO** |

**读数**：

1. MultiTTS **没有「客户端无关的默认音色」**：其 `VoicePair` / `VoiceItem` 两张表**全空**
   （`speaker` 表有 52 条角色）。没被客户端 `setVoice` 时，它 `speak()` 返回 `SUCCESS`
   却不出声、不回调 —— **一个只靠完成回调推进的朗读器会直接挂死**。
2. 一旦选了音色，MultiTTS 的时序是**标准且正确**的：`onStart` → 音频 → **读完才** `onDone`。
3. Google 与 `com.m3tts` 不需要显式选音色即可出声（所以 App 在这两家引擎上「碰巧能用」）。

## ③ App 真实路径时序（debug 包 `com.example.tts_reader`，`voiceId=bdetts_paimeng` 经 prefs 注入）

入口用外部文本（`ACTION_SEND` + `autoSpeak`），第二段在**第一段读到一半时**送入，
复刻 PDF「点句」＝「`stop()` 上一句 + 起新会话」的模式。

```
02:06:00.543  DBG SPEAK_BEGIN: #1 token=2 长度=75
02:06:00.559  D TTS  Utterance ID has started: 7c544571-…
              （朗读中，共 10.4 秒）
02:06:10.965  DBG CANCEL_WAITS: seq=16 取消 2 个在等的插件调用
02:06:10.965  DBG LINES_RUN_START: token=3            ← 新会话开始
02:06:10.965  DBG ENGINE.stop: 有在等的 speak 吗=true  ← 要害：stop() 里有等待者
02:06:10.978  D TTS  Utterance ID has been stopped: 7c544571-…. Interrupted: true   ← 引擎回的是 onStop
02:06:10.978  DBG SPEAK_DONE: #1 token=2 ok=false 占用=10434ms
02:06:10.979  DBG LINES_RUN_EXIT: token=2 历经=11583ms lineIndex=0/1
02:06:10.979  DBG SESSION_END: token=2 （放行等这一代的 await）
02:06:11.534  DBG SESSION_END: token=3
```

**四条硬结论**：

1. **引擎回的是 `onStop`（`Interrupted: true`），不是 `onDone`** —— MultiTTS 在这一点上是
   对的。且 `flutter_tts` 的 `onStop` **不会**完成 `speak()` 的平台 Future
   （`FlutterTtsPlugin.kt:124-137`），所以「引擎把取消当读完」这个假设在 MultiTTS 上**不成立**。
2. 那一拍的「提前返回」来自 **App 自己**：`ENGINE.stop: 有在等的 speak 吗=true`
   → `_completePending()` 同步唤醒 → `SPEAK_DONE ok=false`。**与引擎无关**。
3. `ok=false` 说明 `_awt` 已能识别「这次是被取消的」；问题在于**会话级信号**
   （`whenSessionFinished()` → `SESSION_END`）**不带结束原因**，PDF `_readLoop`
   只能靠 `lastSpeakInterrupted`（会被新会话起点清掉）+ `waited < 100ms` 去猜。
4. 本次实测旧会话**没有**错误推进（`lineIndex=0/1` 未前进）——因为
   `_speakInterrupted` 在 1239 清除前、旧 await 尚未返回；窗口是否落进去取决于时序，
   与 §4.106/§4.107 的静态推演一致。

## ④ 对下一轮的影响（可直接用）

1. **模拟器装置现在可用**：只要给 App 存一个现存音色（`voiceId`），MultiTTS 在
   `emulator-5554` 上能真实出声并给出标准回调。§4.107「尚未闭环的一环：真机才能验证
   `stop()` 打断路径」的前提**不再成立**，可以在模拟器上补跑。
2. **注入音色（不需要动 UI）**：装 debuggable 包后
   `run-as com.example.tts_reader` 写入 `shared_prefs/FlutterSharedPreferences.xml`，
   加 `flutter.tts_settings = {"rate":1.0,"pitch":1.0,"voiceId":"bdetts_paimeng"}`。
   （`_applyVoice` 在 `_voiceId` 为空**或不在当前列表**时静默跳过 → `tts_manager.dart:1651-1659`；
   真机上「换语音包后音色名变了」会直接掉进 MultiTTS 的静默态，属于**真实的兼容风险**。）
3. **上一轮两条探针用例失败的原因**（`integration_test/tts_engine_probe_test.dart`、
   `real_tts_interrupt_test.dart`）：两者都没 `setVoice`，且测试里
   `SharedPreferences.setMockInitialValues({})` → `_voiceId=''` → 未设音色 →
   MultiTTS 静默 → `speak()` 挂满 3 分钟 / 真机③ 不推进。**不是判据的问题。**
   修法：用例里先 `setVoice`（或把引擎切成 `com.google.android.tts` / `com.m3tts`）。
4. **修复方向不变**：给会话信号带上「结束原因」（epoch 或 `_speakUnit` 返回 bool），
   而不是继续在 PDF 侧用时间启发式兜。本次实测为该方向提供了引擎无关的证据。
