# v1.21.55 改动说明 —— 切书后恢复朗读读回上一本书

> 版本：**1.21.55+115** ｜ 日期：2026-10-17 ｜ 基线：v1.21.53+114
> 任务：修「书A暂停 → 打开书B → 恢复却读书A」（EPUB / PDF 皆有，应用内与通知栏两个入口都有）

---

## 一、结论先行

**不是切书逻辑错了，是"另一条朗读路径"没被收走。**

真正坏的是这一条：用户先打开过 B（`_documentId` 已经是 B），
之后去读了 PDF(A) 并暂停，再回到 B —— 此时 `loadDocument(B)` 判断
「同一本书重进」，于是在 `terminateForDocumentSwitch()` 里
**整条 return**，连"终止另一条朗读路径(PDF)"那一步一起跳过了。

结果：通知栏 / 耳机的当前媒体来源**仍然停在旧 PDF(A)** 上，
一按播放就去读 A，而用户正看着 B。

## 二、真机日志（决定性证据）

用户实测日志（2026-10-17 11:54），关键三行：

（`媒体控制[play source=… title=… pdfKey=…]` 与文档库控制栏两个 `onPlayPause`）。

## 三、根因与修法

### 3.1 根因

`TtsManager.terminateForDocumentSwitch()` 原来的结构：

```dart
final switching = nextDocumentId != null && _documentId != nextDocumentId;
if (!switching) return;          // ← 同 id 重进：整条返回
_terminateOtherReadSession();    // ← 终止 PDF 这一步也跟着被跳过
```

§4.60 那条守卫的本意是「**同一本书重进不许打断自己**」，
但它顺带把「另一个会话还占着音频」这件事也放过了。

### 3.2 修法（`lib/tts/tts_manager.dart`）

把两件事**分开判断**：「本管理器要不要自我打断」与「别的路径占着音频要不要收回」。

```dart
final bool otherWasSource =
    identical(audioHandler?.activeSource, PdfReadSession.instance);
final bool otherHoldsAudio =
    otherWasSource || PdfReadSession.instance.isPlaybackActive;

if (!switching) {
  // 同一本书重进：不打断自己（§4.60），但别的路径占着音频要收回来
  if (!otherHoldsAudio) return;
  _terminateOtherReadSession();
  audioHandler?.activate(this);
  _notify();
  return;
}
```

- 用 `stopSound()`（停声 + **保留位置**），符合"换歌要记住进度"的既有语义；
- **不动音频焦点 / 打断逻辑**（v1.21.52 已定稿）；
- §4.60 的行为完全保留：PDF 没占音频时，同 id 重进什么都不做。

### 3.3 顺带修的引擎层隐患（`lib/tts/system_tts_engine.dart`）

`SystemTtsEngine.speak()` 有个重投机制：提交被插件丢弃（返回 0）时，
每 `150ms` 重投一次、最多 8 次（≈1.2 秒）。**原来重投不检查这次朗读是否已作废**，
于是切书后仍可能把上一本书的文本交给系统念出来。

修法：加**代次令牌** `_generation`，`stop()` / `pause()` / 新 `speak()` 各自 +1，
重投前比对；失效就安静结束（不报错、不推进游标）。

> 这一条是"同一现象的另一条可能来源"（归属全对、但引擎里还压着旧文本）。
> 真机日志已经证明主因是 3.1；这条属于**同类的预防性加固**，一并做了并用契约用例守住。

### 3.4 对称缺口：PDF 侧「同一本重进」同样漏收音频（`pdf_read_session.dart`）

修完 3.1 后复核**反方向**，发现 `PdfReadSession.open()` 也有一处早返回：

```dart
if (_documentId == documentId && _pageCount == pageCount) return;  // 同一本重进
```

于是「先前读过 PDF(A) → 中间去读 EPUB(B) → 再打开这本 PDF(A)」这一拍，
不会把音频来源从 `tts-manager` 收回到 `pdf-session` ——
用户看着 PDF，按播放键却读了之前的 EPUB。

**这正是用户说「EPUB、PDF 都复现」的另一半。** 修法：早返回只保留会话状态，
但若此刻音频被**别的**来源占着，就把来源收回来（先让旧来源 `onStop()` 再 `claim`）。
PDF 自己在播/暂停时（`isPlaybackActive`）不做多余动作。

### 4.3 排查中**被否掉的 7 个假设**（供后人省时间）

| # | 假设 | 实测 |
| --- | --- | --- |
| 1 | `playFromCursor()` 经 `_rebindIfCleared()` 绑回旧书 | ❌ 该方法里没有此调用 |
| 2 | 切书后还能走 `resume()` 恢复旧书 | ❌ 切书把 `_speaking` 置 false |
| 3 | 暂停中的 PDF 抢占派发 | ❌ 换书时它已 `isPlaybackActive=false` |
| 4 | 通知栏 `_source` 指向旧 PDF | ❌ 该场景实测已切到 `tts-manager` |
| 5 | 页面入口不校验文档 | ❌ 点 B 章标题后 `holdsB=true` |
| 6 | 真实两页压栈：A 暂停 → 开 B → 点播放 | ❌ `holdsA=false holdsB=true` |
| 7 | 解析窗口期（B 未加载完）点播放 | ❌ `holdsA=false`，`_doc==null` 时什么都不做 |

**其中一条曾经"变红"是测试手法造成的假象**：
第一次用 `pumpWidget` 换掉整棵树来测，A 页被 dispose → 出现 `holdsA=true`；
换成**真实 navigator 压栈**（A 页仍在栈里）后立刻变绿。
**结论：测换书必须用 push 压栈，不能用 `pumpWidget` 顶部替换。**
