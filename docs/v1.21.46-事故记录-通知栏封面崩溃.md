## 一、原始任务与查证结论

任务：通知栏媒体卡片显示当前文档封面（PDF 用渲染首页、EPUB 用自带封面）。

**第一步查证（没改代码）**：

| 查证点 | 证据 | 结论 |
| --- | --- | --- |
| 有没有设过 `artUri` | 全仓库构造 `MediaItem` 只有一处（`tts_audio_handler.dart` 的 `_pushState`），参数里没有 `artUri` | **从来没设过** |
| 设 `file://` 有用吗 | `audio_service-0.18.17`：Dart 侧 `audio_service.dart:1038` 只把 `content:` 原样透传；Android 侧 `AudioService.java:805-811` 对非 content 的 artUri **直接 `artBitmap = null`** | `file://` 传了等于没传 |
| 封面图要不要重做 | 不需要：`DocumentService.extractCover` 早在 v1.21.17 就按类型抽好（EPUB 自带 / PDF 用 pdfrx 渲首页 / TXT 默认样式），落在 `<app_flutter>/covers/<文档id>.jpg` | 只需把已有文件转成系统读得到的 URI |

所以判定是「没设」→ 走实现。**这一段查证是对的，后面错的是实现之后的归因。**

## 二、实现（曾经的样子）

* 新增 `lib/services/audio_artwork.dart`：路径公式 + 绝对路径 → `content://` 换算 + 按文档 id 的缓存。
* `content://` 的来源**没有新增依赖**：复用工程里已有的 FileProvider
  （`AndroidManifest.xml` 的 `DownloadedFileProvider`，authority `<applicationId>.flutter_downloader.provider`），
  它的 `res/xml/provider_paths.xml` 本来就有 `<files-path path="." />`，
  而封面正落在它根下的 `app_flutter/`；那个 provider 类是一行代码都没有的纯子类
  （`class DownloadedFileProvider : FileProvider()`，flutter_downloader-1.11.8）。
* `AudioSessionSource` 只加一个 `documentId`（"是哪本书"），封面怎么来不归来源管。
* 页面侧两处硬编码的封面路径改调 `AudioArtwork.coverPathFor`（公式只有一份）。

自检全绿：`analyze` 0 问题、全量 **1011 通过 / 3 跳过 / 0 失败**（比基线 +23）、
资源自检 OK、lame 自检 OK。**单测全绿 —— 但它在真机上是崩的。**

## 三、三次真机对照（关键证据）

| 包 | 与前一版的差别 | 真机结果 |
| --- | --- | --- |
| `test01` | 完整封面功能 | **点播放即崩** |
| `test02` | **只把 `MediaItem.artUri` 那一行换成 `null`，其余一字未改** | **不崩**（用户确认） |
| `test03` | 封面保留，但把"解析完重推状态"的重入改掉 + 加校验 | **点播放仍崩**（用户确认） |

`test02` 与 `test01/test03` 之间**唯一的差别就是那一行** —— 这是整件事最硬的一条证据：
**崩就发生在这条执行路径上。**

### 崩溃的形态（三次日志一致）

```
位置[PDF起读] … ref=38/13 …
AF[起读] doc=1791905778698996 src=pdf-session …
媒体控制[activate（换源）pdf-session] …
媒体控制[pushState] source=pdf-session playing=true … index=38/286
AF[滚动到位] 偏移=20149 实际=20149
        ← 进程消失，1~3 秒后 ---- app 启动 ----（自动恢复同一本书，再崩，成循环）
```

* **`crash.log` 里没有任何异常**：`FlutterError.onError` / `PlatformDispatcher.instance.onError`
  装了钩子却一条都没记到 → 不是 Dart 异常；
* `adb logcat -b crash` 与 `/data/anr` 也没有对应记录（本机无设备，未取到；
  这一点是**没验到**的部分，如实标出）；
* 崩点不在 `_pushState` 返回之后，而是在**通知栏媒体卡带着 `content://` 去读图**那一段 ——
  即原生进程里的 `AudioService.setMetadata → loadArtBitmap → getContentResolver().openFileDescriptor`。

### 我在归因上犯的两个错（重点）

1. **第一次归因错：当成"重入"**。
   我看 `_resolveArtwork` 在异步解析完成后调 `_pushState()`，判定是"在一次推状态的半途
   又触发一次完整推状态"，于是改成只更新媒体项、不重推。**test03 证明这不对** —— 照样崩。
2. **第二次归因错：当成"EPUB 阅读页"**。
   12:22/12:23 那两份日志里崩点紧跟在"进 EPUB 阅读页"之后，我据此把嫌疑转到 EPUB 页上，
   还请你专门做 EPUB↔PDF 切换实验。**你纠正了：是"点播放"崩**（PDF 也算）。
   两次都是**从相关性直接跳到因果**，而且第二次还让你白跑了一趟实验。

**可以写进规矩的一条**：崩溃点前后那几行日志**不能直接当因果**。
`crash.log` 是**串行队列 + flush 落盘**（`CrashLog._chain`），崩溃时最后几条可能还在队列里没写完，
所以"日志断在哪"只说明"写到哪"，不说明"崩在哪"。要定因果，必须靠**受控对照**（换一个变量），
不能靠日志相邻性。

## 四、为什么加兜底也没用

test03 里我已经把这条路上能加的都加了：URI 形态校验、`mediaItem.add` 外层 `try/catch`、
失败退回"不带封面"再试一次、总开关。**但崩在原生进程里，Dart 侧的 `try/catch` 拦不住** ——
`try/catch` 只能接住 Dart 的异常，接不住原生 abort。

所以唯一的正确处置是**默认关掉、并把源码撤回到已验证的那一份**，而不是"关个开关留着代码"。
