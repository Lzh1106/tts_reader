# 桃花源阅读器（tts_reader）

> 🤖 **本项目由 AI 开发**：代码、测试与文档均由 AI 编程助手编写并自测，人类负责提需求、真机验收与发布。
> 详见文末「[关于开发方式](#关于开发方式)」。

Flutter 3 + Material 3 的文档朗读应用：导入 PDF / EPUB / TXT，用系统 TTS 或云端 TTS 按句、按段、按章朗读，也可以在内置浏览器里直接下载文档并一键导入。

本项目以 **T2S（Text to Voice / Read Aloud）为灵感来源**，结合自身使用场景，重新实现并完善了相关朗读功能。项目独立开发，不含原应用的代码或资源。

功能面覆盖：朗读网页 / PDF / EPUB / TXT，打字朗读、分享即朗读、划词朗读、**复制即朗读（悬浮球 + 快捷磁贴）**，朗读文本预处理规则、自动休眠、阅读排版、书签、双击正文即读、**PDF 点行即读**、导出朗读音频、后台朗读 + 通知栏控制。

- 主题：`useMaterial3: true`，`ColorScheme.fromSeed(seedColor: Color(0xFF6750A4))`，支持亮色 / 暗色 / 跟随系统
- 朗读粒度固定**按句**：底部控制栏是「上一句 / 下一句」，正文逐句高亮，点任意句从该句读起
- 双引擎：系统 TTS（离线）与云端 TTS（OpenAI 兼容接口），云端失败自动降级为系统引擎继续读同一段
- PDF 双模式：原版式（可点页面任意一行从该行读起 + **逐行朗读高亮框**）/ 文本模式（逐句高亮、点句即读、**一键自动排版**）
- 大文件友好：解析结果落盘缓存（第二次打开毫秒级）、解析全在后台 isolate、TXT 分章不做重复复制
- 阅读排版：字号 / 行距 / 字距 / 页边距 / 段间距 / 字体 / 5 种阅读底色，改完立刻生效
- 朗读文本预处理：正则替换规则（`△` → 「三角形」、去掉 `[1]` 这类参考文献编号、不读网址……）
- 自动休眠：无操作 N 分钟后暂停 + 一次朗读满 N 分钟后停止
- 书签与最近阅读：正文任意位置加书签、跨文档跳转、文档库按最近阅读排序
- 导出朗读音频：用系统 TTS 把当前章 / 整本合成成音频文件（存放在系统「音乐」目录）
- 复制即朗读：悬浮朗读球（可拖动）+ 两个快捷设置磁贴 + 开机自启
- 平板 / 大屏：PDF 页面按屏幕自动放大、正文限宽居中、导航栏移到侧边
- 内置浏览器：自带起始页（搜索框 + 搜索引擎切换 + 历史 / 收藏夹 / 快捷方式）、
  地址栏与标题同层、主题跟随、返回键走网页历史

## v1.21.12：把「被停止」和「读完了」彻底分开（治根）

### 上一版做了什么、还差什么

v1.21.10 是在 **PDF 那条路**上加了一道「最短合理时长」判据（收到 <100ms 的"读完"
就丢弃）—— 那是**止血**。这一版把根因也修了。

### 根因

系统 TTS 插件把**「取消」和「读完」走了同一条回调**，而且没有参数区分：

```dart
_tts.setCompletionHandler(_handleFinished);
_tts.setCancelHandler(_handleFinished);   // 取消也走它
```

于是「被停止掐掉」会被上层**当成"读完了"**，位置就往前推一句 —— 连点几次累积成
"跳 5~10 句"。真机实测：54% 的"读完"只有 **0~48 毫秒**，而真读完一句要 1~6 秒。

### 现在

在**共享层**（`TtsManager`）加了一个明确的「**这一拍是被打断的**」标记：

- `stop()` / `pause()` 时若正有一次朗读在飞 → 标记为**打断**（不是读完）；
- 朗读主循环在拿到引擎返回后**紧跟**检查这个标记 → 被打断就**不推进位置**；
- 每次新会话开始才清掉标记（不在每句的清里清，否则会当场抹掉刚判定的打断）。

PDF 那条路的两道判据现在是**叠加**的：
1. **打断标记**（可靠、与朗读时长无关）—— 治根；
2. **<100ms 时长判据** —— 兜底，应对极端短的假完成。

TXT / EPUB 走的是同一条共享循环，所以**同时受益**，不需要分别改。

## v1.21.10：修「点句之后跳好几句」——丢弃假的"读完"信号

### 问题

在 PDF 里点屏幕上的句子（或短时间连点几下），读到的位置会比点的那句**往后多跑几句**，
连点会累积，严重时像"跳了一整页"。而同样操作在 TXT / EPUB 上几乎不出现。

### 根因（真机日志实测）

系统 TTS 插件**有时会提前报告"这一句读完了"** —— 真机抓到的数据：

| | 实测 |
|---|---|
| 真的读完一句 | 1 ~ 6 秒 |
| 假的"读完" | **0 ~ 48 毫秒**（最短 0ms） |
| 假完成占比 | **54%**（112 次里有 60 次 ≤200ms） |

一次假"读完"，位置就往前推一句 —— 连点几次就累积成"跳 5~10 句"。

> 为什么 PDF 明显、TXT/EPUB 少见：**PDF 每读一句都会先叫一次"停止"**，
> 而"停止"会顺手触发一次完成回调；TXT/EPUB 是整章连续读，一次会话只叫一次停止。
> 所以同一条底层信号，PDF 踩到的频率高一个数量级。

### 现在

PDF 那条路加了一道**「最短合理时长」判据**：一句汉字最短也要 ~80ms 才发得完，
所以**收到不到 100ms 的"读完"就丢掉、不往下推**，让出一小段再看一眼。
最多连丢 3 次（有上限，绝不会因此把朗读卡死）。

**只动了 PDF 这一条路**，TXT/EPUB 用的那条底层完成信号**一行没改**。

### 效果

| 验证 | 结果 |
| --- | --- |
| 单测 · 假完成被丢弃 | ✅ 800ms 内只发出 2 次朗读（没有判据时能刷完 3 句） |
| 单测 · 真完成不受影响 | ✅ 200ms 的完成照常推进；连读 3 句不会被卡死 |
| 真机 · 假完成压力测试 | ✅ 1.2 秒内 30 次假完成只前进 7 句（无判据时是几十句） |
| 真机 · 真完成对照 | ✅ 总时长 1233ms / 1224ms，丢弃重试 0 次，正常推进 |
| 真机 · EPUB 对照 | ✅ 路径未改动，行为不变 |

**预期**：每次点句最多多推 1 句，**不会再累积成 5~10 句**。

## v1.21.8：按方块键后，通知栏卡片会变成「未在播放」

### 问题

读着书按文档库的方块键，应用里确实停了，但**下拉通知栏那张播放卡片没变** ——
还显示着书名和暂停按钮，看起来像还在播。用户的原话：

> 通知栏的控制和文档库的控制不同步，在控制栏点击方块时，通知栏应未在播放。

### 原因（两个，各坏一半）

**① 读 PDF 时，通知栏根本没收到通知。**
应用里有两个互相独立的播放开关（一个给 TXT/EPUB，一个给 PDF）。通知栏「当前跟谁」
只认一个来源；PDF 在播时来源就是 PDF，这时 TXT 那边发来的所有通知都被一道闸门挡掉了。
而 PDF 自己停止时**一步状态都不推**。两边一叠加，通知栏就**完全没被通知过**。

**② 读 TXT 时通知了，但用的方式会把卡片弄没。**
原来「没有会话了」推的是一个「空闲(idle)」状态。而在 `audio_service` 里，
`idle` 不是一个普通状态 —— 它出现时库会直接**停掉前台服务**，也就是**卡片消失**。
所以那条路要么把卡片弄没、要么状态对不上。

### 现在

- 按方块键：**状态变成「未在播放」**（标题显示「未在播放」，只剩一个停止按钮）；
- **卡片保留**，不会被销毁；
- 三种情况都验过：只读 TXT / 只读 PDF / 先 TXT 后 PDF 的跨类型切换；
- 想关掉卡片：点卡片上的停止按钮，或直接划掉。

> **和 v1.21.6 的区别**：v1.21.6 是「**完全不碰**通知栏」；这一版是
> 「**碰，但只改状态、不销毁卡片**」。这两件事在 API 层面本来就是分开的
> （`idle` = 销毁开关，「未在播放」= `ready` + 播放中为假），混用就会出事。

## v1.21.7：连点相邻句不再串位 + 控制栏不再显示已停的那本书

### 1. 短时间内连点相邻的句子，不再「滚到随机位置、从错误位置开始读」

**问题**：快速点几下相邻的句子（或连按「下一句」），屏幕会滚到莫名其妙的位置，
而且读出来的不是刚点的那句。同一本书里偶尔发生，句子越密越容易碰上。

**原因**：点一下之后，「位置」要等**声音真的停下来**才会更新（实测几十毫秒）。
在那之前再点一下，程序读到的还是**上一次的旧位置**，于是每次都算出同一句 ——
点得越快，越容易全部落回同一句上，最后只有最后一次生效、目标还是错的。

**现在**：点下去的那一刻就先把「你想去哪」记下来，后续判断一律以它为准。
连点三下相邻句，目标依次前进（不会再挤成同一句），位置也是真的落到了第三句。

> 按「下一句」按钮和直接点屏幕上的句子，两条路都修了。

### 2. 切到别的书之后，底部控制栏不再显示已经停掉的那一本

**问题**：读着 PDF 去文档库打开一本 TXT 开始读，回到文档库时，
底部那条控制栏显示的、按钮操作的，还是**刚才那本 PDF** —— 但实际在读的是 TXT。

**原因**：PDF 被切走时**声音停了、但会话故意留着**（为了你切回去还能接着读，
位置要记住）。而控制栏判断「该显示谁」时用的是「会话在不在」——
于是那本**已经停掉的** PDF 一直被当成"正在读的那本"。

**现在**：控制栏判断「该显示谁」改成看**是不是真的在播**（暂停也算）。
已停掉的书不再占着控制栏；正在读的书正常显示。

> 方块键的语义**没有改**：按方块键仍然是「彻底终止」——
> 连保留的位置一起清掉（因为按它表达的是"我不读了"）；
> 而只是切到别的书、不按方块键，上一本仍然会保留位置，等你切回去接着读。

## v1.21.6：方块键「按一次就够」+ 首次教程更新

### 方块键：按一次，应用内控制栏立刻消失

**问题**：按一次方块键声音停了，但底部控制栏不消失，**要再按一次**才消失。

**原因**：应用内部其实有**两个**互相独立的播放开关 —— 一个给 TXT / EPUB，
一个给 PDF。而控制栏是「哪个在播就只显示哪个」的单边结构，方块键也就**只关了当前那一个**。
两个都在的时候，第一次只关掉一半，所以看起来像「没生效」。

**现在**：一次按下去，两个一起关，控制栏立刻消失。只有 TXT、只有 PDF、
以及「先读 TXT 再读 PDF」三种情况都验过。
**没有任何一边在播时再按，是安全的空操作。**

> ✅ **通知栏的播放卡片照旧保留**（显示「未在播放」）—— 这是你要的常态，本版没有动它。
> 方块键只清应用内的会话，不碰通知栏。

### 首次使用教程：更新了过时的地方

教程弹窗一直还在、正常触发。这次核对后改了两处：

- **方块键的两种用法分开写了** —— 原来只写「方块键结束朗读」，但它在
  **文档库**和**阅读页**其实是两种行为：文档库里按是「结束朗读、控制栏整条消失」，
  阅读页里按是「只收起成小圆盘，会话保留，点播放接着读」。原来没区分，
  按了会发现跟说的不一样。
- **新增一条「朗读中的新能力」** —— 把最近几版加的东西补上：

  朗读位置自动记住（下次进来接着读）、以及**打开另一本书开始朗读时上一本会自动停下并记住位置**
  （就像音乐播放器换歌）。

## v1.21.5：PDF 高亮框重做、主题跟随取色、快进不再乱翻、跨文档「换歌」语义

这一版把上一轮改到一半的五项任务收尾并**逐项在真机上验过**。用户能感知到的变化：

### 1. PDF 高亮框：逐行独立，不再是一个斜跨多行的大框

原来一句话跨 3 行会画成**一个盖住三行的大矩形**，还常常把中间的标题行一起罩进去。
根因有两个，都很隐蔽：

- 高亮是按**原文下标区间**去扫全页字符的，而 PDF 的文字层里「页脚 / 标题」的下标
  与视觉顺序**无关**（页脚恒为 0），于是区间把别行的字捞了进来；
- pdfrx 给「行尾换行符」和「行首空格」的占位盒，高度是**很小的正值**
  （打印出来是 `0.0`）。这些盒子被当成正常文字吸进上一行，把整行的下边界
  拖到下一行去 —— 所以「一行」其实横跨两行。

现在：高亮按**几何**分行，**每行一个独立矩形**，水平位置各随各的（句子跨 3 行就是
3 个块，第 3 行只有末尾两字宽）；零高占位盒按「高度不足半磅」剔除；
断行符不再夹进朗读文本（原来会把「出版」读成断开的「出 版」）。

**实测**（319 页真实书）：修复前「并块行 99 / 覆盖违例 97」→ 修复后**全部为 0**。

### 2. 高亮配色跟随主题（含动态取色）

高亮底色不再写死浅蓝，改为从当前主题的 `primaryContainer` 成对派生；
系统开着「动态取色」时会跟着壁纸的强调色走。暗色底上按**同一色相**派生一套
深/浅配（不再写死深蓝），保留「亮度差 > 0.3」的可读性约束；半透明与内收距离沿用原值。

### 3. 连点「下一句」不再让页面乱翻

翻页闸门拿不到总页数（构造时文档还没打开），于是**每一次翻页请求都被静默丢掉**，
画面实际靠另一条旁路滚动 —— 连点就是好几个滚动动画抢同一个位置，看起来像抽风。
现在闸门能拿到真实页数，跟随朗读统一走闸门。

**实测**：连点 20 次「下一句」，当前页与高亮位置始终一致，20 次只发生 **2 次**翻页。

### 4. 朗读位置恢复：退出、重进、中断续读都能回到原处

朗读位置改为按文档独立落盘（显式操作立即写、连续推进防抖写、停止/暂停/结束前强制写）。
从文档库重新进入、或结束朗读后再次进入，都会定位到上次的位置（只定位，不自动重播）。
句子下标会**校验后再用**，旧位置指向不存在的句子时退回该页开头，不会串到别的句子。

### 5. 切换文档 = 音乐播放器换歌

用户的原话是「切换文档原理应和音乐播放器切换歌曲一样」。这条**之前是坏的**：

- 从 A 换到 B 时，**A 根本没被停**（换书只换了「当前文档」的记录，没有任何终止动作）；
- 更糟的是 A 的朗读还在跑，而它推进的是 **B 的坐标** —— 会把 B 的位置带偏；
- 反过来「PDF 读着去开 TXT」也一样不停，两本书会同时出声。

现在在「**新文档的朗读会话被创建的那一刻**」显式终止上一本：停止（不是暂停）+
把上一本的位置写回文档库 + 新的文档只读自己的状态。同**一本**书重新进入不会
打断朗读（退出阅读页继续读的既有行为保持不变）。

**实测**（真机三向）：TXT→TXT、TXT→PDF、PDF→TXT 三种切换，旧的那一本全部停止且位置已记住。

### ⭐ 最重的一条：朗读会在一本书中间自己「读完」

319 页的《共产主义ABC》**读到第 8 页就不再读了**，而且会话认为「整本读完」。

原因是**两层叠加**：

1. 第 9 页是**空白页**，而跳页的逻辑把「下一页没有文字层」当成了「到文档末尾」；
2. 修掉第一层后才暴露第二层 —— 跳过空白页要往后看好几页，可文字层的缓存

现在改成**分块往后推**（抽一块立刻就地检查，不回头依赖缓存），并且区分

- PDF 是**借**文本朗读的引擎发声的，用完留下的痕迹让「是否还有会话」

**实测**：`方块键 → clear()` → `ttsActive=false pdfActive=false` → `控制栏还在=false`。

## v1.21.3：给位图加像素预算（清晰，但内存不失控）

v1.21.2 把位图提到物理像素后，先实测了一遍代价 —— 结论是**当前场景没问题**：

| 测量项 | 结果 |
| --- | --- |
| 连翻 45 页内存 | PSS 从 151 MB 涨到 159 MB（**基本平稳**） |
| 单页位图 | 1036 × 1470 ≈ 152 万像素，解码约 5.8 MB |
| 快速翻页掉帧 | 系统侧**零**「Skipped N frames」 |
| 静止 / 翻页 CPU | 0% / 满一个核（模拟器软渲染放大了这个数） |

但实测同时暴露出一个**没被覆盖的路径**：pdfrx 是按**当前布局尺寸**渲染的，
位图字节数按尺寸的**平方**增长。现在是「一页铺满视口宽度」，一旦以后加
**捏合缩放**、或在**平板大屏**上，单页像素数会翻倍上涨 —— 200% 缩放就能把
单页推到 24 MB，而 Flutter 的 `imageCache` 默认预算只有 100 MB。

所以加了一条**像素预算**：

```
单页位图上限 = 400 万像素（解码约 16 MB）
```

- 没超上限 → **原样返回**（不误伤清晰度，当前 152 万像素用得很宽松）；
- 超了 → **等比缩小**（只降分辨率，不改宽高比，显示不会变形）。

上限的取法有依据：当前实测 152 万，留了 **2.6 倍**余量给缩放；同时保证
`imageCache` 至少能放 4 页，不会一滑就抖。这两条都写成了断言。

### 又修了一个用户可见的 bug：文字层加载完成后界面不刷新

排查上面那条时发现一个更容易碰到的毛病：**凡是打开时文字还没抽完的页，
会一直显示成「没有文字层」，点它没反应** —— 快速滑到新的一页时最容易遇到。

原因有两处：抽完文字后会话**没有通知界面**，而阅读页**也没监听**会话。
于是「这一页现在能点了」这件事根本传不到界面。两处都补上了。

现在正文页点句的实测输出：

```
各页=[2:有层, 3:有层]
会话位置=PdfSentenceRef(1, 10, "编印：莱茵学社编译室莱茵杂志社编译组")   期望句下标=10  ✓
```

## v1.21.2：修「PDF 显示发虚」—— 位图没按物理像素渲染

用户反馈「手机解析 PDF 显示不够清晰」。

### 原因

渲染出来的**位图只有显示区域的 1/2.75**，被放大后才铺满屏幕，所以字边缘发虚。
实测数据（手机 1080×2340，dpr = 2.75）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 位图尺寸 | 376.7 × 534.6 | **1036.0 × 1470.1** |
| 逻辑尺寸 | 376.7 × 534.6 | 376.7 × 534.6 |
| 位图 / 显示 | 1.000 | **2.750**（= dpr） |
| 达到物理像素 | ❌ | ✅ |

注意：**字的大小本来就是对的**（页面已铺满视口），问题纯粹是清晰度 ——
所以没有动初始缩放（HANDOFF §4.68 那条铁律不受影响）。

### 为什么会出现

`pdfrx` 的 `PdfPageView` 有一条容易踩的规则：**一旦你给了
`pageSizeCallback`，渲染尺寸就完全按它的返回值来，它自己不再乘
devicePixelRatio**（`pdf_widgets.dart` 的 `_updateImage`）。
而那张位图会被 `RawImage` 拉伸到**逻辑**尺寸显示。

所以回调返回什么，位图就是什么：

```
返回逻辑尺寸        → 位图只有物理像素的 1/dpr → 被拉伸 dpr 倍 → 糊
返回逻辑尺寸 × dpr  → 位图正好铺满物理像素     → 清晰
```

同一个 `pageSizeCallback` 之前因为「点击坐标偏移」被改成返回逻辑尺寸
（HANDOFF §4.93 的坑 2），当时只考虑了**命中测试**要的是逻辑尺寸，
没意识到**渲染**要的是物理尺寸 —— 一个参数担了两个职责。

### 修法与它为什么不影响点句

```dart
pageSizeCallback: (pixelSize, page) {
  final dpr = MediaQuery.devicePixelRatioOf(context);
  return Size(logical.width * dpr, logical.height * dpr);  // 位图 = 物理像素
}
```

命中测试的换算用的是**逻辑**尺寸（`_scale = _rendered.width / pageSize.width`，
`_rendered` 来自 LayoutBuilder 约束），而组件占的**逻辑**尺寸不因为这个
返回值改变（`RawImage` 被 `AspectRatio` 包着），所以屏幕→PDF 点的换算不用改。

实测回归：点句 `scale=0.898`、命中句 0、高亮 `(0,4)` —— 与修复前完全一致。

### 新增：把清晰度用数值守住

真机上「清不清晰」没法用截图对比来守（CI 里不可靠），所以新增设备用例
`integration_test/pdf_resolution_verify_test.dart`，在真实 319 页 PDF 上断言：

```
位图宽度  ≥  显示宽度 × devicePixelRatio
```

并留了一个诊断口子 `PdfPageLayer.renderDiagnosticsListener`
（位图 / 逻辑 / 显示 / dpr 四个数一起给出来，排查时不用猜）。

### 顺手修掉：正文页点句「点了没反应」

验证点句时发现**正文页**（每页几十行小字）点句没反应，封面页却正常。

原因：抽取某一页文字时，如果这一页**正在被预取**，后到的请求会拿到
`null`，于是被当成「这页没有文字」直接返回 —— 表现就是点了没反应。
封面页字少、撞不上；正文页预取与点击几乎同时发生，才稳定复现。

已改成「同一页的并发请求共享同一次加载」，并新增设备用例
`integration_test/pdf_body_tap_verify_test.dart` 专门点**正文页**守住：
断言点中的是哪一句、会话位置就是哪一句（实测 `句下标=10` 完全命中）。

## v1.21.0：PDF 朗读完全重构（独立实现，不复用旧路径）

按需求从零实现了一套 PDF 朗读，**不再参考旧实现**：
渲染用 Canvas，文字做成可点击的透明文本层，点哪句读哪句。

### 架构：分层（与需求的 1~4 条一一对应）

```
lib/features/pdf_reading/
├── pdf_text_layer.dart      字符 → 行 → 句子；命中测试；跨页合并（纯逻辑，可单测）
├── pdf_page_layer.dart      渲染位图 + 上层透明文本层（命中测试 / 高亮）
├── pdf_reading_page.dart    整篇：加载、点读、TTS、高亮跟随、回到朗读位置
└── open_reading_screen.dart 按文档类型分派（PDF → 新实现；TXT/EPUB → 原阅读页）
```

| 需求 | 实现 |
| --- | --- |
| 1. Canvas 渲染 + 透明文本层 | `PdfPageView`（PDFium）渲染位图，上面叠一层自绘 `CustomPaint` 文本层 |
| 2. 点击合并碎片成完整句子 | 逐字符盒 → 按**几何**分行 → 按**中英标点**分句（等价 `Intl.Segmenter`） |
| 3. speechSynthesis + 先 cancel 再 speak | `TtsManager.speakText`（内部 `_generation++` 作废上一轮 = cancel+speak） |
| 4. 高亮 + 回到朗读位置 | 按行合并的半透明色块；滚出视野时浮出按钮，点击平滑滚回 |

### 换掉渲染引擎：Syncfusion → pdfrx（PDFium）

要「透明文本层」就必须拿到**逐字符包围盒**。实测 `syncfusion_flutter_pdfviewer`
的 `PdfTextLine` 只到**行级**，做不出精确到字的命中；`pdfrx` 的
`PdfPageText.fragments[].charRects` 给的正是逐字符盒，所以渲染也一并换成它
（同一个引擎出位图与文字，天然对齐）。

> ⚠️ 版本约束：本工程 Flutter 3.24.5 / Dart 3.5.4，**只能用 pdfrx 1.0.101**
> —— 1.2+ 起要求 Flutter ≥3.29 / Dart ≥3.7，装不上。

### 三个踩过的坑（都会让功能直接不可用）

1. **`PdfRect` 是左下原点**（PDF 原生坐标，`top > bottom`），Flutter 是左上原点。
   不翻 Y 轴就会高亮上下颠倒、点上面的字命中下面的字。统一在 `loadTextLayer`
   里翻好：`flutterTop = pageHeight - pdfTop`。
2. **`pageSizeCallback` 的第一个参数是设备像素**，不是逻辑像素
   （实测 376.7 逻辑宽 → 回调给 1036，dpr≈2.75）。拿它算缩放会大 2.75 倍，
   点击坐标整体偏离 → **点不中任何字**。正确来源是布局约束。
3. **构建链**：pdfrx 1.x 的 Android 构建走 CMake，需要 NDK + CMake（本机原本
   都没有，已装），另有两个环境坑（见 `tool/patch_pdfrx_symlink.ps1`）：

## v1.20.7：修「文本模式点下一句导致文本框定位失败」

用户报：「文本模式朗读时，点击切换下一句，有概率导致文本框定位失败」。
**「有概率」的来源找到了**，而且是一个一直存在的根因。

### 根因：手指一碰正文就关掉自动跟随 —— 包括「点句朗读」

```dart
// 旧代码
onPointerDown: (_) => _pageAutoFollow = false,
```

本意是「用户滑动浏览时不要抢页面」。但**点句子朗读 / 点句切换也是
`onPointerDown`**，于是每点一次就把自动跟随关掉；而 `_followCursor`
开头就有 `if (!_pageAutoFollow) return` —— **从此再也不翻页**。

后果链：

```
点句 → _pageAutoFollow = false
     → 朗读读到**下一页**的段落
     → _followCursor 直接 return，页面不翻
     → 那一页从没被 ListView 建出来
     → 高亮框的锚点不存在，_readingGeometry() 返回 null
     → 用户看到「框不见了 / 定位失败」
```

为什么是「有概率」：只有当朗读推进**跨页**时才暴露；同一页内推进看不出来。

设备实测快照（`debugFollowSnapshot()`）：

```
第 30 次点击后 {cursor: (0, 5, 0), block: 6, pageOfBlock: 1, pageIndex: 0,
               anchorBuilt: false, autoFollow: false, ...}   ← 不翻了
修后：        {… autoFollow: true, pageTurning: true …}
收敛后 rect=Rect.fromLTRB(22.0, 73.5, 778.0, 131.5)          ← 框在屏幕上
```

### 修法：区分「点」与「拖」

只有手指移动超过 `kTouchSlop` 才算「用户在拖动浏览」，才关自动跟随；
单纯点一下（点句朗读、点句切换）不再影响跟随。
「用户滑走就不跟」的原有行为完全保留。

### 顺带加固：定位失败不再被静默丢弃

同一个问题里还有第二个隐患：`_scheduleReveal` 原来在「已有定位在跑」
或「180ms 节流窗口内」时**直接 return，把这次定位丢掉**，而
`_userScrolling` 闸门又要等 2.5 秒 —— 两者叠加就会「这一次定位彻底没发生」。
现在：

- 拒掉的调度记进 `_revealWantBlock`，窗口过后**一定补一次**；
- 新增 `_revealWithVerify`：定位完成后**验证是否真的落进视野**，
  没落上就重试（最多 3 次），而不是默默结束；
- `_runPendingReveal()` 挂在跟随周期里，欠着的定位下一轮就补。

回归用例：`test/reader_follow_reliability_test.dart`（连点 30 次「下一句」后
必须收敛到可见范围；跨页连点 90 次，每次收敛后框都要在屏幕内）。
## v1.20.6：修「目录跳转导致快速翻页」

用户报：「朗读时通过目录跳转，有概率定位失败导致快速翻页」。

### 根因：`animateToPage` 会把中间每一页都真的滑过去

定位本身没错（跳完确实落在目标章）。问题出在**翻页动画**上：

```dart
controller.animateToPage(target, duration: 260ms)   // target 可能是第 148 页
```

从第 1 页跳到第 148 页，`animateToPage` 会**真的连续渲染 147 页** ——
看着就是「页面疯狂往后翻」。实测轨迹（每 40ms 采样一次）：

```
修前：0 → 60 → 101 → 125 → 137 → 144 → 147     ← 逐页动画的痕迹
修后：0 → 147                                    ← 瞬时落位
```

而且中间每帧都会触发 `PageView.onPageChanged`，可能再叠加新的翻页请求。

**修法**：只给「相邻一两页」保留动画（正常跟读时看着自然），
**跨度超过 2 页就直接 `jumpToPage` 瞬时落位** ——
目录跳章、书签跳转、通知栏拖进度都是这种大跨度。

> ⚠️ 改成瞬时落位时踩到一个必须一起处理的坑：
> `jumpToPage` 会**同步**触发 `PageView.onPageChanged`，而那里会 `setState`；
> `_turnPageTo` 又可能正是在 **build 期间**被 `_followCursor` 调的 ——
> 于是直接抛「setState() called during build」。
> 所以 `jumpToPage` 与 `setState` 都放到**帧后**执行
> （与 PDF 那边的 `_goToPdfPage` 同样处理）。

回归用例：`test/reader_toc_jump_test.dart`（跳到第 50 章 / 最后一章，
断言页码单调、不翻过头，并打印轨迹供人工核对）。
## v1.20.5：修 PDF 点句真正生效 + 目录切章朗读 + 换书终止上一本

三个用户报的问题，第一个是**根因级**的：

### 1. PDF「点击即读」还是不生效 —— 找到了真正的原因

之前两轮都在改「怎么判点击」，真正的断点在**坐标换算前的页数判断**：

```dart
// 旧代码
final pageCount = _pdf.pageCount;   // ← 这里是 0！
```

实测（真实 319 页 PDF、模拟器）打印出来的值：

```
DIAGCONV 视口=Offset(210.0, 305.7) pageCount=0
         pageSize=Size(392.1, 567.8) scroll=Offset(0.0, 0.0) zoom=1.0
```

**PDF 已经渲染出来、`_pdfReady` 也为真了，但 `_pdf.pageCount` 仍然是 0** ——
插件控制器要更晚才把它填上。而换算函数第一句就是
`if (pageCount <= 0) return null;`，于是**每次点句都在换算那一步返回 null**，
表现就是「点了完全没反应」。

修法：页数**优先用解析结果**（PDF 里一章就是一页，`_doc.chapters.length`
一直都在），只有解析结果为空时才退回 `_pdf.pageCount`。

> 教训：不要信「插件应该已经就绪」这种假设。`_pdfReady` 只代表
> `onDocumentLoaded` 回调过，不代表控制器每个字段都填好了。

### 2. 通过目录切换章节只跳转不朗读

方块键的语义是「关闭朗读模式」，走 `endSessionAndClear()`，
而它会把 `TtsManager._doc` 清掉（控制栏收起正是以 `hasSession` 为假的依据）。
之后从目录点章节 → `speakFrom` → `_runBody` 第一句
`if (doc == null) return` —— **静默返回，只跳转不朗读**。

以前是在阅读页各处手动补 `_ensureDocumentBound`，但朗读入口太多
（点句、点行、章标题、目录、播放键、通知栏……），漏一个就出一次
「点了没反应」。现在改成**在 TtsManager 里统一兜住**：

- `loadDocument` 记一份「最近绑定的文档」；
- `_restart` / `resume` 开头调 `_rebindIfCleared()`：只动「被清空」这一种情况，
  文档还在时什么都不做，不会打断正常朗读。

### 3. 朗读时切换文档，上一本还在响

在朗读 A 的时候打开 B（文档库点另一本、书签跳另一本），阅读页会 push
一个新实例，A 那个页面还活着 → 读 B 时 A 的声音一起响。

修法：阅读页的 `_ensureDocumentBound` 里加一条判断 ——
**正在朗读的是别的文档就先把上一本终止掉**，再绑新文档。
放在这个统一入口，点句 / 点行 / 章标题 / 播放键都覆盖到了。

| 未进入朗读模式时单击 | **不动作**，只提示一次「双击句子即从这里开始朗读」 |
| 控制中心的**方块键** | 结束朗读**并退出朗读模式** —— 之后要再**双击**才能读 |

> 方块键的语义（用户要求）：终止朗读 = 退出朗读模式，
> 所以「单击切句」随之失效，想再读必须**再双击一次**。
> 两种模式行为一致，不存在「PDF 要双击、文本只要单击」的差异。

实现要点（**这里是踩了两轮才走通的地方，别再改回去**）：

**文本模式**：正文是 `Text.rich`，每句一个带 `TapGestureRecognizer` 的 span。
双击由段落级的 `onDoubleTap` 承担 —— 同一处快速点两下时，
句子 span 的单击识别器会**输给**段落的双击识别器，
所以 `onSpeakSentence` 只会收到真正的单击，不需要自己按时间窗判。

**PDF 原版式**：**绝对不要用插件的 `onTap`**。它的回调条件里带
`!_isDoubleTapped`（`pdfviewer.dart:3693`）—— **识别为双击时根本不回调**。
所以「双击 = 两次 onTap」永远凑不出来，v1.20.0/v1.20.1 两次都栽在这里。
现在改成从 `Listener` 的原始指针事件自己判点击 / 滑动 / 长按 / 双击。

坐标换算（关键，已用真实点击在设备上校对）：

```
页内 = 视口 + scrollOffset      （zoomLevel == 1；scrollOffset 是逻辑像素）
```

| 视口 y | 插件报的页内 y | 差 |
| --- | --- | --- |
| 386.2 | 591.1 | 204.9 |
| 214.7 | 550.4（期间往下滚了） | 335.7 |

两次差值都恰好等于当时的 `scrollOffset.dy`。换算抽成了纯函数
`viewportToPagePosition`，由 `test/pdf_viewport_to_page_test.dart`
用上面这组实测数据精确断言。

也因此关掉了插件的**双击缩放**（两者抢同一个手势）；放大改用双指捏合。

### 3. PDF 加载速度：文字抽取改成多 isolate 并行

实测剖析（《共产主义ABC》319 页，4.5 秒）：

```
总=4557ms   抽取=4523ms   分段=22ms
```

**文字抽取是唯一的大头（99%）**，而它与调用方式无关
（逐页 4204ms / 一次性 3860ms / 分块 3744ms，都是同一份真实工作量），
所以只能多核并行：

- 页码切成 N 段（N = CPU 核数，夹在 2~4），每段在独立 isolate 里各自打开一份 PDF 抽取；
- 页数 < 24 或并行失败 → 自动退回单线程逐页（慢一点但一定能出结果）；
- **实测 4.5s → 2.9s**，结果完全一致（8346 段、318 页行信息）；

### 4. 允许其它媒体打断朗读 + 耳机控制


需求：「增加双击想朗读的句子进入朗读模式，进入朗读模式后单击其他句子进行切换。」

> ⚠️ **实际做出来的是「单击」**，原因如下（不是偷懒，是插件限制）：
> Syncfusion 26.2 的 `onTap` 回调条件是
> `if (!_isDoubleTapped && _canInvokeOnTap)` —— **它识别到双击时根本不回调**。
> 所以「双击」这个动作在插件这一层拿不到任何事件，
> 「双击进入 + 单击切换」在 26.2 上无法实现。

最终行为（PDF 原版式与文本模式**一致**）：

| 操作 | 行为 |
| --- | --- |
| **单击**文本层的某一句 | 进入朗读模式，并从那一句开始读（首次弹一句提示） |
| 继续单击其他句子 | 切换到那一句 |
| 控制中心的**方块键** | 结束朗读并退出朗读模式 |

插件的 `onTap` 已经把**滚动 / 长按过滤掉**了，能回调上来的一定是「用户真的点了一下」，
所以不会再出现「滑一下就误读」的问题。
双击的净效果 = 只读一次（插件不给第二次回调），也不会重复朗读。

**PDF 侧的实现坑**：`onTap` 给的 `details.pagePosition` 是**页内坐标**，
与解析时记下的文字行外框同一套坐标系，可以直接命中。
26.2 的 `PdfViewerController` **没有**公开的「视口坐标 → 页内坐标」换算
（`convertScreenOffsetToPageOffset` 是更高版本才有的），所以别自己从
`Listener` 的指针事件算坐标 —— 拿不到页内坐标就命不中文字行。

**文本侧**：正文是 `Text.rich`，每句一个带 `TapGestureRecognizer` 的 span。
单击句子 → 切到该句；双击段落 → 也进入朗读模式（`onDoubleTap`）。

### 1. 高亮框乱跳 / 快速向后翻页：改成「一个判据，分档处置」

原来有两个回调各自滚页面（跟随 + 兜底定位），互相抢位置 —— 这就是「框上下乱跳、
连带着快速向后翻页」的根源。现在合成**唯一一套判据**（`_readingGeometry` 量出
当前句在本页的相对位置），然后：

| 框的位置 | 处置 |
| --- | --- |
| 在视口 30%~72%（舒服区） | **什么都不做**（这是「不乱跳」的关键） |
| 掉到视口下方 | 向下跟随（**绝不上滚** —— 上滚就是乱跳的来源） |
| 跑到视口上方 / 贴近页顶**且光标已在本页最后一段** | **强制翻到下一页**，不被人为滚动打断 |
| 用户主动跳转（点句 / 快进 / 跳章） | 双向跟随（往回跳也跟） |

「贴近页顶就翻页」必须同时满足「本页读到头了」：只按位置判会误翻 ——
页面刚打开、或某段正好停在靠上位置时框本来就在上方。

**有 4 个落到别的句子**上 —— 这正是「排版后从文档库进入定位不准」。

### 7. 允许其它媒体打断朗读 + 耳机控制

| 设置 | 默认 | 作用 |
| --- | --- | --- |
| 允许其它媒体打断朗读 | 开 | 朗读时申请音频焦点：音乐 / 视频 / 导航播报 / 来电能暂停朗读，对方结束后自动接着读 |
| 耳机按键：按句 / 按章 | 按句 | 「上一首 / 下一首」键 = 上一句 / 下一句（或跨章） |

**之前的真实缺陷**：只在启动时 `session.configure(speech())` 配了音频属性，
**从来没有 `setActive(true)`** —— 也就是从没申请过音频焦点。
结果两个都不对：别的应用出声时不会把我们压低 / 暂停（听书和音乐一起响），
来电也不会把我们暂停。

现在：

- **开**：朗读开始申请焦点，暂停 / 停止 / 结束时释放（不释放会把别的应用一直压着）；
  收到系统的 `pause` 打断就暂停，打断结束后**只有「是系统让我们停的」才自动继续** ——
  用户自己按的暂停不会被重新拉起来；
- **关**：不申请焦点，各放各的（想边听书边放音乐时用）；
- 开关改完**立即生效**，不用重启应用。

耳机控制走 `audio_service` 的 MediaSession：播放 / 暂停键 → 暂停或继续朗读；
上一首 / 下一首 → 按设置走「按句」或「按章」（长按快进 / 快退 → 上一页 / 下一页）。

> 说明：Android 把耳机按键**固定映射**成媒体键（播放/暂停、上一首、下一首），
> 应用无法任意重映射 —— 所以这里只做「接到朗读动作上 + 让用户选粒度」。

## v1.18.1：修「返回朗读位置不准 / 排版后回不到原句」

**验证结果**：`flutter analyze` 零问题，`flutter test` **458 项全部通过**（新增 2 项）。

两个都是**真 bug**，而且根子在同一个地方：段落的锚点（`GlobalKey`）没有创建。

### 1. 原格式下也有概率不能准确返回朗读位置

「用户停在哪」是靠量「视口顶端是哪一段」得到的，而这一步依赖段落上的锚点。
重构分页版面时，锚点只剩「读取」没有了「创建」（旧实现里是跳转逻辑顺便建的），
于是 `_anchors` **恒为空** → 量不到任何段落 → `_lastSpot` 永远是 `(0,0,0)`
→ 退出写回的进度是 0 → 重进回到开头。

同一个原因还让「回到朗读页」按钮点了不滚（`ensureVisible` 找不到锚点）。

修法：在渲染段落时按需建锚点（`_anchors.putIfAbsent(blockIndex, GlobalKey.new)`）。

### 2. 记录的时机：`dispose` 里量不到

即使锚点齐了，原来「退出前再量一次」也是无效的 ——
**Flutter 会先把 `ScrollPosition` 从 `ScrollController` 上摘掉**，
`dispose` 时 `hasClients` 已经是 false。

改成「活着的时候记」：滚动时、翻页落地后的下一帧各记一次，
`dispose` 只负责把最后一次算好的值写盘。

### 3. 翻页动画途中会量到「正在退场的那一页」

翻页动画期间相邻两页同时挂在树上，各段全局 Y 是叠在一起算的。
不加限制就会量到旧页 → 「翻到第 6 页却记住第 5 页的位置」。
现在只认属于**当前落定页**的段落。

### 4. 自动排版后「返回朗读页」回不到原句

重排会改变段落下标，而原来的顺序是「先定位 + 建分页，**再**排版」——
于是 `_lastSpot`（用户停留位置）留在重排前的坐标系里，
`_pageIndexForParagraph` 也按重排前的段落算，两者混用就错位。

改成**先排版、再按重排后的坐标系定位**：重排后用「同一句话」把位置映射过去，
`_lastSpot` / 朗读游标 / 分页下标三者从此同源。

实测（每页 10 段、120 段的文档，翻到第 6 页后退出）：

```
退出前：controller.page=5  进度=0.4167
退出后：controller.page=5  cursor=(0,50,0)   ✓ 同一页、同一段
```

顺带修掉一个**假失败源**：`PageController.page` 从 0 开始、界面页码从 1 开始，
测试里混用会写出差一页的断言。

## v1.17.10：修「切下一句概率性快速翻页」+ 暂停时也能翻页

**验证结果**：`flutter analyze` 零问题，`flutter test` **444 项全部通过**（新增 2 项长文本回归）。

### 1. 切换下一句时概率性快速向后翻页（多页长文本下复现）

根因是**翻页判定用的页码在翻页动画途中就已经变了**：

- `_pageIndex` 读的是 `PageController.page`，翻页动画进行到一半时它已经指向新页；
- 而「本页读完了吗」用 `_pageIndex` 去取「本页最后一句」——动画途中取到的是
  **下一页**的范围，于是「刚翻过去就被判成又读完了」→ 接着往后翻。

修法两条：

| 改动 | 说明 |
| --- | --- |
| 新增 `_displayedPage`（只在 `onPageChanged` 动画落地时更新） | 「读完本页」的判定改用它，翻页途中不再拿错页的范围 |
| 新增 `_lastAutoTurnTarget`（同一目标页只自动翻一次） | 朗读推进很快时 `_followCursor` 会被反复调用；只靠翻页闸门不够，闸门一放开就会对同一目标再翻一次 |

另外把「用户自己翻页」与「自动跟读」分开：用户手动翻页（按钮 / 滑动）后
**暂停自动跟随**，想跟回来按「回到朗读页」——与 PDF 原版式的 `_pdfFollowing` 同义。

实测（多页长文本，连点 12 次「下一句」）：

```
页码轨迹 [1, 1, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2]
         └ 第 1 页读完才翻 ┘ └ 之后一直停在第 2 页，没有连翻
```

### 2. 朗读暂停时允许翻页

翻页是「看」的操作，与朗读状态无关；只有**自动跟读**翻页才需要朗读在进行。

- 「上一页 / 下一页」按钮在暂停时照常可用；
- 只有「到第一页 / 最后一页」才会置灰；
- 左右滑动本来就不受朗读状态影响，保持原样。

实测：朗读开始 → 暂停 → 点「下一页」翻到第 2 页 → 点「上一页」翻回第 1 页，全部正常。

## v1.17.9：自动排版变成可切换的固化开关

**验证结果**：`flutter analyze` 零问题，`flutter test` **442 项全部通过**（新增 5 项）。

### 改动

「自动排版」按钮以前是**一次性**的：点一次把被折行切断的句子接回整段，按钮随即消失，
下次进来又是原样。现在是一个**固化开关**：

| 行为 | 说明 |
| --- | --- |
| **点一次 = 排版** | 把 PDF 里被硬折行切断的句子按语义接回整段 |
| **再点一次 = 恢复原排版** | 换回解析出来的原始章节结构 |
| **不点就不改** | 不点按钮时，当前生效的排版不会被任何操作改动 |
| **退出重进保持** | 选择按文档落盘，重进阅读页自动应用上次的选择 |
| 状态可见 | 排版生效时按钮是**选中态**（点亮），提示语变成「恢复原排版」 |

实测（单测断言）：

```
排版前：Page 0 first sentence begins here and the|second sentence begins here and it is also|broken across two lines...
点一次：Page 0 first sentence begins here and the typesetter broke it across two lines, then the second sentence...
再点一次：回到排版前的形态
重进（开着）：排版形态      重进（关着）：原排版形态
```

### 实现要点

- 开关存在 `StorageService`（按文档 id 记，`reader_auto_format_docs`），
  而不是只活在阅读页内存里 —— 否则「退出重进保持」就无从谈起。
- 原始章节结构留在 `_originalDoc`，撤销时换回去；重排结果本身**不缓存**，
  需要时从已解析的文字行信息现算（很快）。
- 两个入口都要补应用：解析完成时（大 PDF 会直接进文本模式）与**切到文本模式时**
  （小 PDF 初始是原版式，自动排版只在文本模式下可用）。

### 阅读区从「连续滚动」改成「真·分页版面」


**1. 该高亮的那句不高亮（`Object.hash` 碰撞）。**
段落视图缓存句子的 `TextSpan` 时，把「当前句下标 + 明暗 + 段落 + 配色 + 字号」

## v1.17.5：退出在哪，重进就在哪（PDF 与文字模式都一样）

**验证结果**：`flutter analyze` 零问题，`flutter test` **422 项全部通过**。

### 需求

「PDF 转文字模式，在退出时在 PDF 页面，重新进入时就在退出时的页面；文字模式也是这样。」

### 关键区分：**朗读到哪** ≠ **用户停在哪**

原来记录的只有「朗读游标」，而用户完全可能只是翻看、没朗读；也可能读到一半又
翻到别处去了。现在单独跟踪一个**停留位置**（`_lastSpot`）：

| 模式 | 停留位置是什么 | 什么时候更新 |
| --- | --- | --- |
| PDF 原版式 | **当前页码**（一章即一页） | 翻页 / 滚动时，以及退出瞬间再读一次控制器 |
| 文字模式（含 PDF 转文字） | **视口顶端那一段** | 用户滚动时、退出瞬间 |

退出时把它换算成进度写回文档库；重进时优先按它还原。

### 顺带修掉的三处

1. **「读到末尾退出 → 重进被扔回开头」**：旧实现有「进度 ≥ 99.5% 视为已读完，
   从头开始」的规则，与「退出在哪就在哪」冲突，已去掉。
2. **重进时 PDF 跳页被丢掉**：解析完成时 PDF 视图常常还没加载完，那时的
   `jumpToPage` 会被忽略（表现就是「重进回到第 1 页」）。现在先记下待跳页码，
   等 `onDocumentLoaded` 再跳。
3. **同一个 id 再次打开时被旧游标覆盖**：`TtsManager` 是单例，它记的
   `activeDocumentId` 只要 id 相同就一直算数。新增 `holdsDocument()` 精确判断
   「这本书是否正被持有」，并把「内存游标」与「写回进度」按**位置靠后**取一个 ——
   两者都可能过期，取更近的一次在两种情况下都对。

### 实测

- 文字模式：进度 60% → 重进落在第 180 段；进度 99.9% → 落在末尾第 299 段；
  进度 0 → 从头。
- PDF 原版式（真机）：停在第 6 页退出 → 重进**回到第 6 页**。

3. 阅读进度；
4. 从头开始。

只认同一本书：`TtsManager` 是单例，读别的书时它记的是别的书的游标 ——

## v1.16.0：解析提速、自动排版、PDF 句高亮、控制中心折叠、浏览器一体化

**验证结果**：`flutter analyze` 零问题，`flutter test` **384 项全部通过**（v1.15 为 337 项）。

### 1. 大文件解析：第二次打开几乎是瞬间

解析一本书要读整个文件、解码编码、切章、分句、逐页抽 PDF 文字层。**同一份文件每次
打开的结果完全一样**，所以只有第一次需要真解析 —— 解析结果会以紧凑二进制存进
`app_flutter/parse_cache/`，之后打开直接从磁盘读回结构。

实测一本 6.8 MB / 3000 章 / 108000 句的小说：

```
首次解析   254 ms
命中缓存    63 ms     ← 缓存 6.9 MB
```

手机上的差距更大（单核慢、内存带宽低，首次解析要好几秒）。失效判据有三条，
任何一条不符都会自动退回真解析，不会读到旧结构：

| 判据 | 说明 |
| --- | --- |
| 文件指纹 | 路径 + 字节数 + 修改时间（换文件、重新下载、编辑过都会变） |
| 缓存格式版本 | 字段布局改动时递增 |
| 解析器版本（`DocumentService.parseRevision`） | 解析规则改动时递增 |

缓存文件带 CRC-32：被写坏或截断时直接丢弃重解析，不会解出半本书。
删除文档时缓存一并清理。

### 2. PDF 解析：每页只抽一次文字

旧实现每页要调三次抽取（正文一次 + 行位置两次，而取行位置内部又会重复做一遍
字距/行合并）。现在正文与行位置都从**同一次** `extractTextLines` 派生，一本 800 页
的 PDF 少抽 1500 多页；顺带的好处是「页面上的行」与「正文里的句子」天然对齐。

### 3. TXT 分章：去掉「章数 × 行数」的重复复制

旧实现每章都做一次 `lines.sublist(a, b).join('\n')`，上千章的小说这一步就要几十秒。
现在只记「每行起始下标」的整数数组，正文按区间惰性截取（`_LineIndex`）。

### 4. PDF 文本模式：一键「自动排版」

PDF 里没有段落标记，抽取出来常常是**一行一段**（一句话被拆成好几段，朗读还会平白
多出停顿）。文本模式下多了一个「自动排版」按钮，把被排版硬折行切断的句子接回整段。
判据按可靠性排序（宁可多分段，也不要把两段粘成一段）：

| 判据 | 结论 |
| --- | --- |
| 行尾是 `。！？` 或收尾引号 | 说完了，另起一段 |
| 行中间出现「句末标点 + 新句子开头」 | 软换行被抽取器接回同一行，作者在这里分段 |
| 行尾是 `，、；：`、开引号、破折号 | 明显没说完，一定接上 |
| 下一行以标点或小写字母开头 | 它只能是续行（新段落不会这么开头） |
| 排到接近右边界（≥88%） | 被排版硬折了，下一行是续行 |
| 其余（行短、无标点、下一行像新句子） | 当成段落末行，保守断开 |

另外顺手处理：英文断词（`inter-` + `national` → `international`）、英文续行补空格、
每页重复的页眉页脚、纯页码行、项目符号 / 编号开头的新段落。

实测一台模拟器上的效果（一页三行被折行的正文）：**6 段 → 1 段**；本来就一句一段的
正文保持不变，界面提示「无需重排」。只影响本次阅读、不写进缓存，可以再点一次。
排查判据问题时，`ParagraphReflow.debugSink` 会把每一次「另起一段」的原因打出来
（哪条规则命中、上一行右边界多少、原文与排版结果各是什么）。

### 5. PDF 原版式：正在朗读的句子有高亮框

原版式是渲染好的页面位图，但**页面坐标与屏幕坐标的换算是已知的**：
页面在视口里居中，再叠加缩放与滚动偏移。所以现在朗读时会在页面上画出
当前句的高亮框（一句话跨行时框住连续几行），随滚动 / 缩放跟着动。
句子被滚出视野时框自动隐藏，顶部字幕条仍在。

### 6. 朗读自动翻页：不再和人工操作打架

原来有两个问题叠在一起，表现是「有概率快速翻动」：

1. **翻页没有闸门**：朗读推进比翻页动画快时（一句几百毫秒 vs 翻页 300 ms+），
   会出现「一句一次 `jumpToPage`」，上一次动画还没结束就重置；
2. **人工操作不优先**：用户刚滑走，朗读立刻把页面拉回来，两边来回抢翻页通道。

现在：翻页期间有闸门（目标页未确认到达就不再发新请求，带 1.2 秒兜底超时）；
用户一碰页面就暂停自动翻页并留 1.5 秒冷却，想跟回去按「回到朗读页」即可。

### 7. 底部控制中心可折叠

朗读时用户主要看正文，控制栏占着屏幕下方一大块很碍事。现在多了一个收起按钮：
折起来只剩「播放/暂停 + 当前位置 + 展开」，折起来也照样能暂停。

### 8. 平板：PDF 页面按屏幕大小自动放大

平板上「适应宽度」会让 A4 页面只占视口一小块、四周全是灰边。现在：
竖屏按页宽比例放大、横屏按页高比例放大，上限 1.6 倍（再大就一屏看不到几行字）；
**手机不受影响**（保持 1.0）。放大倍数由解析时记下的页面尺寸算出来，
不额外解析一遍 PDF。

### 9. 内置浏览器与应用一体

## v1.15.0：导入时把文件收进应用目录

**验证结果**：`flutter analyze` 零问题，`flutter test` **337 项全部通过**，
设备层 **29 项全部通过**（新增一条真机用例：「缓存副本 → 复制进书库 → 删掉源文件后仍能解析」）。

### 为什么必须复制

Android 上 file_picker 交给应用的**不是**用户选的那个文件，而是它复制到缓存目录的副本：

```
/data/user/0/<包名>/cache/file_picker/<时间戳>/<文件名>      ← picker 的临时副本
/data/user/0/<包名>/app_flutter/books/<文件名>               ← 现在导入后会存到这里
```

缓存目录随时可能被系统清掉（存储空间紧张、用户点「清除缓存」），
那时文档库里的书记录还在、文件却没了 —— 打开就是「文件不存在」。

### 规则

| 情况 | 处理 |
| --- | --- |
| 源文件在应用私有目录之外（picker 缓存、其它应用的文件） | **复制**进 `app_flutter/books/`，**保持原文件名** |
| 源文件已在应用私有目录内（下载目录、上次导入的副本） | 不复制，直接用原路径 |
| 书库里已有同名同大小的文件 | 复用那一份（重复导入同一本书不会存两份大文件） |
| 同名但内容不同 | 加 ` (1)`、` (2)`，**不覆盖** |
| 复制失败（空间不足等） | 照常导入、引用原路径，并提示「复制到应用目录失败」 |
| 从文档库删除文档 | 书库副本一起删掉；下载目录 / 外部原文件不动；副本被别的文档共用时保留 |

下载完自动入库也走同一套规则（见 `lib/services/library_storage.dart`），
所以「下载到系统下载目录」的书也会有一份稳定副本进书库。

真机实测：

```

DEVICE_VERIFY[adopt] 缓存副本=/data/user/0/com.example.tts_reader/cache/picker_cache/红楼梦 (曹雪芹) 第一回.txt
DEVICE_VERIFY[adopt] → /data/user/0/com.example.tts_reader/app_flutter/books/红楼梦 (曹雪芹) 第一回.txt copied=true
DEVICE_VERIFY[adopt] 源文件删除后解析：章=2 编码=UTF-8 首段=天还没亮他就出门了，路上一个人也没有。
```

## v1.12.0：下载与导入都保留文件原名

**验证结果**：`flutter analyze` 零问题，`flutter test` **311 项全部通过**，
设备层 **26 项全部通过**（新增一条「原名带空格/中文/括号也能原样落盘」的真机用例）。

### 下载：只清洗真正非法的字符

以前文件名是这样处理的：

```dart
name = name.replaceAll(RegExp(r'[\\/:*?"<>|\s]+'), '_');
```

`\s` 把**空格**也换成了下划线 —— `红楼梦 (曹雪芹) 第一回.pdf` 会变成
`红楼梦_(曹雪芹)_第一回.pdf`。现在改成只替换文件系统真正不允许的字符
（`\ / : * ? " < > |` 与控制字符），空格、中文、括号、`#`、`+`、`%`、`&`、`'` 一律原样保留：

| 情况 | 处理 |
| --- | --- |
| 服务端给了名字（Content-Disposition） | 用它，只清洗非法字符 |
| 服务端没给 | 用 URL 末段（去掉查询串、按百分号解码） |
| 没有扩展名 | 按 MIME 补一个（`12345` → `12345.pdf`） |
| 重名 | 按 Android 下载器的习惯加 ` (1)`、` (2)`，**不覆盖也不改名** |
| 名字过长 | 只截断基名，扩展名留着（ext4 单名 255 字节，中文一个字 3 字节） |
| 结尾的点 / 首尾空白 | 去掉（部分文件系统会吞掉结尾点） |

真机实测（服务端用 RFC 5987 给了一个带空格、中文、括号的名字）：

```
DEVICE_VERIFY[filename] 服务端名字=红楼梦 (曹雪芹) 第一回.pdf → 实际用=红楼梦 (曹雪芹) 第一回.pdf
DEVICE_VERIFY[filename] 重名时第二个文件=红楼梦 (曹雪芹) 第一回 (1).pdf
```

### 导入：书名用选择器报的原始文件名

Android 上 file_picker 会把选中的文件**复制到缓存目录**再交给应用
（`cache/file_picker/<时间戳>/<名字>`），拿不到名字时它写的是 `unamed`。
所以书名改用选择器报的**原始文件名**，而不是缓存副本的基名（后者只在拿不到原名时兜底）。

下载完自动入库的书名也是同一个规则（原名去掉扩展名），
命名规则集中在 `lib/services/file_naming.dart`，下载与导入两侧共用、单测覆盖 18 项。

## v1.11.0：TXT 正文不再是乱码

**验证结果**：`flutter analyze` 零问题，`flutter test` **293 项全部通过**，
设备层 **25 项全部通过**（新增一条真机解析 GBK / UTF-16 的用例）。

### 乱码是怎么来的

原来只有两条路：**严格 UTF-8 成功就用它，失败就 Latin-1 逐字节硬解**。一本 GBK 小说于是有两种结局：

1. 字节序列不是合法 UTF-8（多数情况）→ Latin-1 硬解 → **整本乱码**；
2. 字节序列**恰好**是合法 UTF-8 —— 中文少、文本短的文件很容易撞上 → 连异常都不抛，
   悄悄解成「拉丁字母 + 注音符号」那种乱码。

第 2 种就是「**有概率**乱码」的来源：同样的书，内容不同、长短不同，结果就不一样。

### 现在的做法（`lib/services/txt_decoder.dart`）

```
BOM（UTF-8 / UTF-16LE / UTF-16BE）
  → 严格 UTF-8：能过且不像乱码 → 直接用（绝大多数文件走这条快路）
  → 没有 BOM 的 UTF-16：按 NUL 字节分布加分
  → 候选编码（GBK / Big5 / Latin-1 / UTF-16LE / UTF-16BE）各解一遍，
    按「像不像正常正文」打分选赢家，换编码必须领先 0.15 分（避免误判）
```

打分的依据是字符构成：中文（含中文标点、全角）权重最高，ASCII 次之，
「拉丁扩展 / 注音 / 组合符 / 希腊 / 西里尔 / 私用区」这类**乱码高发区**权重很低甚至是负分，
非法字节（U+FFFD）重罚。

**不会误判真实外语文件**：俄语、希腊语、法语这类文件的「异种文字块」只有一个
（乱码才会同时混好几个块），而且它们的打分很高，所以仍然按 UTF-8 处理 ——
单测里专门钉了这三门语言。

GBK / Big5 解码用 `enough_convert`（纯 Dart，因为解析跑在 isolate 里，
不能用任何插件或平台通道）。识别到的编码会写进诊断日志
（设置 → 诊断日志里能看到「TXT 编码：GBK」），一眼就能判断这本书是什么编码。

真机实测（同一段中文，三种编码）：

```
DEVICE_VERIFY[encoding] GBK    → encoding=GBK      章=2 首段=天还没亮他就出门了，路上一个人也没有。
DEVICE_VERIFY[encoding] UTF-16 → encoding=UTF-16LE 章=2 首段=天还没亮他就出门了，路上一个人也没有。
DEVICE_VERIFY[encoding] UTF-8  → encoding=UTF-8    章=2
```

顺带修了一个相关的小问题：英文 TXT 的「Chapter One / Chapter Two」这种**拼写数字**章名
以前识别不出来（只认 `Chapter 12` 和罗马数字），现在也认了。

### 2. EPUB：改成「spine 保正文 + nav/NCX 提目录」

这里先修掉一个隐藏很久的问题：**epubx 是按 NCX 建章的，不是按 spine**。

| 处理 | 说明 |

| 标题优先级 | 目录标题 > 正文的 `h1`~`h3` > `<title>` > 「第 N 章」——很多书的每个文件 `<title>` 都是同一个书名，直接用它会出现一堆重复章名 |
| 层级 | nav 的嵌套 `<ol>` / NCX 的嵌套 `navPoint` 都保留（缩进显示） |
| 分组标题 | nav 里没有链接的 `<span>`（如「第一卷」）会补到子项标题前：「第一卷 · 第一章」 |
| 锚点 | 指向同一文件内锚点的条目也进目录（标题是真的，跳转到该章开头） |
| 路径归一化 | `../`、`./`、URL 编码、`/` 开头都处理，才能和 OPF 的 href 对上 |

实测（真机，EPUB3 只带 nav 文档）：


### 6. 顺带修掉一个大 bug：多段纯文本朗读只读第一段

熄屏验证时发现：网页朗读 / 复制即朗读的**多段**文本，读完第一段就整个停了。根因在
`TtsManager._handleEngineCompletion` —— 它把 `_oneShot` 当成「只读一条」的判据，
而纯文本队列为了 `resume()` 也把 `_oneShot` 置真（真引擎在每段结束时既唤醒
`speak()` 的 Future 也会调这个回调），于是每读完第一段就被收尾。
现在判据改成「纯文本队列后面确实没有下一条」才收尾，文档朗读完全交给主循环。

单元测试之前抓不到它：假引擎的 `setCompletionHandler` 是空的。现在假引擎照真引擎
（`SystemTtsEngine._handleFinished`）的行为在每段结束时回调，退回旧逻辑立刻可见：

```
（旧逻辑）Expected: <4>  Actual: <1>   每条分片都读到一次
（修复后）All tests passed!
```

### 1. PDF 也有句子高亮与「从哪一句开始读」

先说清一个技术前提：**原版式那张页面位图上画不出对齐的高亮框**。
Syncfusion 的 PDF 视图不暴露「PDF 坐标 → 屏幕坐标」的换算（没有公开的 `TransformationController`，
页面的缩放、内边距、滚动都是私有的）。所以按需求做了两条路：

| 场景 | 行为 |
| --- | --- |
| 点底部「播放」 | 自动切到**文本模式**并给一条提示：这一模式才有逐句高亮、点任意句可从该句读起（右上角随时切回原版式） |
| 留在原版式 | **点页面上的任意一行 → 从那一行所在的句子开始读**；朗读时顶部显示「字幕条」，把当前这一句高亮显示出来 |

点句的实现：解析 PDF 时同时用 `PdfTextExtractor.extractTextLines()` 记下**每一页每一行的文字与外框**，
再用 `SfPdfViewer.onTap` 给的 `details.pagePosition`（相对页面的坐标，原点在页面左上角）去命中某一行，
最后把那一行的文字在正文里定位到具体的段与句。设备实测（Android 14 模拟器）：

```
DEVICE_VERIFY[pdf-tap] fraction=0.3 speaking=true cursor=(0, 12, 0)
DEVICE_VERIFY[pdf-tap] fraction=0.7 speaking=true cursor=(0, 37, 0)
DEVICE_VERIFY[pdf-tap-log] 点句：第 1 页 坐标 298,240 → 行「Line 13 ...」→ 第 13 段第 1 句
DEVICE_VERIFY[pdf-tap-log] 点句：第 1 页 坐标 298,602 → 行「Line 38 ...」→ 第 38 段第 1 句
```

点得更靠下 → 从更靠后的句子读起，说明两套坐标是同一套、也没有上下颠倒。
（文字行只保留前 4 万行，超大 PDF 的「点句」会失效，但不影响朗读本身。）

## v1.6.x：受 T2S 启发的功能完善

T2S 是本项目的灵感来源之一。本项目结合自身架构与使用场景，独立复刻并完善了文本预处理、自动休眠、阅读排版、书签、网页朗读、音频导出与外部朗读入口等功能；不含原应用代码或资源。

### 1. 朗读文本预处理

朗读前按顺序套用规则表，**只改写送去合成的字符串**，阅读页显示的仍是原文。

| 内置预设 | 作用 |
| --- | --- |
| 去掉方括号内容 | `\[[^\]]*\]` → 删除 |
| 不朗读维基参考文献 | `\[\d+\]` → 删除 |
| 把 △ 读成「三角形」 | 将 △ 替换为「三角形」 |
| 把箭头读成「到」 | `[→➔➜]` → 到 |
| 不朗读网址 | `https?://…` → 删除 |
| 去掉 Markdown 标记 | `[*_`~]{1,3}` → 删除 |
| 还原网页空格实体 / 连续空格压成一个 | — |

- 设置页 →「朗读文本预处理」：可增删改、拖动排序、逐条开关；
- 编辑对话框**实时预览**：显示正则是否合法、在样例文本里命中几处、替换后的结果；
- 替换串支持 `$1`~`$9`、`$&` 回填分组，`$$` 表示字面 `$`；
- 规则写坏（非法正则、把文本放大到离谱）只跳过该条，绝不影响朗读；被删空的句子直接跳过，不会给引擎送空串。

### 2. 自动休眠

- **空闲自动暂停**：无操作 1/3/5/10/15/30/60 分钟后自动暂停（翻页、点句子、按控制键都算「有操作」）；
- **定时停止**：一次朗读满 15/30/45/60/90/120 分钟后停止（听书定时用）；
- 到点会弹一条提示（「已 10 分钟没有操作，自动暂停」），否则「自己停了」会像故障；
- 两条阈值都关闭时**不建任何定时器**（测试环境最怕悬挂定时器）。

### 3. 阅读排版

字号 12–30、行距 1.2–2.4、字距 0–3、页边距 0–48、段间距 0–24，字体可选系统 / 衬线 / 无衬线 / 等宽，
阅读底色 5 种：跟随主题 / 纸白 / 羊皮纸 / 护眼绿 / 夜间。设置页带**所见即所得的样例正文**，改完阅读页立刻生效。

自定义底色下，朗读高亮与章节标题条不再使用主题的 `primaryContainer`（深色底上会糊成一片），
而是取自正文色的半透明叠加。

### 4. 书签与最近阅读

- 阅读页右上角一键在当前位置加书签 / 取消书签，图标随状态变化，书签按钮带数量角标；
- 书签面板同时列本文档与**其它文档**的书签：本文档的点了直接跳转（游标 + 视图一起对齐），
  其它文档的点了打开那本书并落到书签位置；
- 书签记录正文片段与创建时间，上限 500 条，删除文档时一并清理；
- 文档库支持三种排序（最近阅读 / 导入时间 / 标题），卡片显示「上次 3 小时前」；
- **继续阅读**：打开文档时自动接着上次的进度（读完的从头开始），并把视图滚到该位置。

### 5. 网页朗读：双击正文段落即读 + 翻译本页

注入脚本给正文块级元素打 `data-t2s-node` 标（排除导航 / 页眉页脚），600 毫秒内连点同一个元素就把
该段文字回传原生，直接开读。`data-t2s-node` 是网页朗读注入脚本使用的内部属性名。

JS 侧回传用的桥方法名与原生侧注册的名字在代码里是**同一个常量**（`WebSpeakScript.handlerName`）——
这两处一旦不一致，双击会静默失效（不报错、也不出声），所以专门有单测守着。

浏览器菜单另有「翻译本页（Google 翻译）」：把当前页地址**整体编码**后拼进 Google 翻译的整页翻译入口
（`web_translate.dart`）。非 http(s) 页面（起始页、about:blank）会提示无法翻译而不是拼出一个坏地址。

### 6. 导出朗读音频

设置入口在阅读页右上角菜单：范围可选**当前章 / 整本**，显示预计文件数与时长，可随时取消。

- 用系统 TTS 的 `synthesizeToFile` 合成，文件落在系统媒体库的「音乐」目录，命名 `书名-001.wav`（序号即播放顺序）；
- 导出前会按句子切片（≤240 字）——系统 TTS 单次合成长度有限，切片保证不丢字；
- 导出的是**预处理之后**的文本，听感与播放一致；
- 单片失败不中断整次导出，逐片回报进度与失败数；
- 与朗读共用系统 TTS，导出前会先停掉朗读，避免互相打断；
- 插件在合成失败分支里**不会给返回值**，所以每片都套了 60 秒兜底（否则整次导出会永久挂住）。

> 当前导出格式为 WAV，本工程未内置 MP3 所需的 LAME 编码器。

### 7. 复制即朗读：悬浮球 + 快捷磁贴 + 开机自启

在别的应用里复制文字，点悬浮球即可朗读；本项目提供完整的 Android 原生实现：

| 组件 | 说明 |
| --- | --- |
| `FloatingSpeakService` | 前台服务（`foregroundServiceType="specialUse"`）+ 可拖动悬浮球；点击朗读、拖动换位置并记住；复制后弹一下提示可以读 |
| `ClipboardSpeakActivity` | 透明界面，**取剪贴板的唯一可靠途径**（见下方「关键约束」） |
| `C2sSpeakTileService` | 快捷设置磁贴：一键朗读剪贴板 |
| `C2sToggleTileService` | 快捷设置磁贴：开关悬浮球（`TOGGLEABLE_TILE`，没授权时点一下直接跳授权页） |
| `C2sBootReceiver` | 开机 / 应用更新后自动拉起悬浮球 |
| `tts_reader/c2s` 通道 | Flutter 读写配置、申请悬浮窗权限、开关悬浮球、朗读剪贴板 |

**关键约束（Android 10+）**：只有**获得输入焦点的应用**才能读到剪贴板内容，后台服务读到的永远是 null。
所以悬浮球/磁贴被点之后启动一个透明界面去取词——而且**不能在 `onCreate` 里读**（那一刻窗口还没焦点，
拿到的同样是 null），必须等 `onWindowFocusChanged(true)`，并带 1.2 秒超时兜底。
设备验证记录：`BAL_ALLOW_VISIBLE_WINDOW`——正是「有可见悬浮窗」让这次后台启动界面被系统放行。

## v1.4.1：修复「点朗读没反应 / 卡住」的调度缺陷 + 三种朗读的真机验证

### 1. 根因：等待插件的登记键用错了变量

`TtsManager` 用「打断令牌 + 代次」来作废旧朗读循环，同时维护一张「正在等插件返回」的登记表，
以便用户按停止时能立刻把旧等待取消掉，而不是干等 30 秒超时。问题出在登记键上：

```dart
// 错误写法：用「游标当前的朗读代次」当登记键
final generation = _generation;        // ← 这个值会在朗读推进、读完收尾时变化
_pendingWaits[generation] = cancel;
...
_cancelWaitsBelow(_generation - 1);    // ← 于是把刚落下的新等待也一起取消了
```

`_generation` 表示的是「游标现在属于哪一代」，它在 `_stopAtEnd()`、`_fail()`、以及每一次
`_restart()` 里都会变。用它当登记键的后果是：**开始朗读时，新循环自己「停掉上一段声音」
的那次等待，会被这次朗读的收尾逻辑当成旧等待取消掉**，`_run()` 于是提前返回：

- 界面没有任何反应，也不报错（`error` 还是 null）；
- 游标停在原地，一句都不会读出来。

现在改成用**单调递增的操作序号**登记（`_waitSeq`），并只取消「序号更小」的等待：

```dart
final seq = ++_waitSeq;            // 本次等待的序号，落定后不受后续操作影响
_pendingWaits[seq] = cancel;
_cancelWaitsBelow(++_waitSeq);     // 新操作只取消比它更旧的等待
```

### 3. 修复「朗读卡死 / 闪退」的根因：插件调用没有超时

这是本轮最主要的修复。`flutter_tts` 与 `just_audio` 都走 platform channel，插件侧**不回复**时（系统 TTS 引擎未安装、被系统回收、蓝牙断开、引擎忙）对应的 `Future` 永远不会完成。原来的实现是裸 `await`：

```dart
await _tts.awaitSpeakCompletion(true);   // 不回复 → 永久挂起
await engine.speak(text);                // 不回复 → 朗读循环永久卡在这一句
await _activeEngine.stop();              // 不回复 → 停止按钮、返回键一起卡住
```

于是表现为「点朗读之后界面无响应」，进而被系统判定为 ANR 而闪退。现在统一加了兜底：

| 调用 | 上限 | 超时后的行为 |
| --- | --- | --- |
| 单次朗读 | 30 秒 | 按朗读失败处理 → 触发云端降级 / 报错并停下 |
| 引擎初始化、语速、音调、音色 | 8 秒 | 按失败处理，界面提示可检查系统语音引擎 |
| 枚举语音列表 | 10 秒 | 退化为空列表（不影响朗读） |
| 暂停 / 停止 | 不等回复 | 立刻下发不等回复（幂等指令，等它只会拖住 UI） |

另外两条配套措施：

- **等待可取消**：用户按停止或跳到新位置时，旧循环挂在插件上的等待会被立刻取消（`_cancelPendingWaits`），不用等满 30 秒；
- **不留悬挂定时器**：超时实现没有直接用 `Future.timeout()`（它在「操作永不完成」时不会取消内部定时器），而是自己等「完成 / 超时 / 被取消」三者先到者，另两条路都会撤掉定时器。

### 4. 修复「用目录跳转后闪退」的下标越界风险

目录跳转会把「章节 / 页」换算成列表块下标，而朗读游标可能来自上一份文档（切文档、重新解析、通知栏拖动进度）。原来这条链路上没有任何夹取：一旦文档与块列表错位，越界下标流进 `ListView.builder` 的 `itemBuilder` 就是 `RangeError` 闪退。现在：

- `_chapterBlockIndex` / `_paragraphBlockIndex` 全部夹取到有效范围，绝不返回越界值；
- 段落块取值前校验章、段下标，越界退化为空占位；
- 目录面板返回的章 / 段下标再夹取一次才喂给朗读游标；
- 解析完成后**先**绑定文档再绑定朗读，两者同源；
- `_jumpToBlock`（跳转定位）整体加了 try/catch：跳转失败不影响朗读与其它交互；
- 底部控制栏的位置文案对段落下标也做了夹取。

> 说明：这两类闪退（目录跳转、朗读中）本机没有真机/模拟器，无法复现用户现场的那一次崩溃，因此**不能断言已经修掉了用户遇到的那一个具体崩溃**。上面是按代码逐条排查后确定的真实缺陷（尤其是无超时这一条，在测试环境里已经实测会把调用永久挂住），并配了回归测试。若仍闪退，请抓一份 `adb logcat`：`PlatformDispatcher.onError` 现在会把未捕获异常打到日志里（关键字「桃花源阅读器 未捕获异常」）。

## v1.3.0：文本层朗读、EPUB 兼容解析、PDF 双模式

早期版本参考同类朗读应用的使用体验，逐步完善了文档文本层朗读、句子级高亮、后台朗读、通知栏控制与可拖动进度。

### 1. PDF 文本层检索与朗读

解析时逐页统计，给出可朗读性判断：

```
hasTextLayer = 抽到字符数 ≥ 20 且 有文字的页数 × 5 ≥ 总页数     // 即至少 20% 的页有文字
```

| 场景 | 表现 |
| --- | --- |
| 有文本层 | 正常朗读，阅读页底部显示页/段位置 |
| 无文本层（扫描件） | 阅读页顶部横幅提示「未检测到文本层（扫描件）」，文档库卡片打上「无文本层」标记；原版式仍可翻看 |
| 结果持久化 | `Document.hasTextLayer` 写回文档库，避免每次打开都重新判断 |

### 2. PDF 双模式：原版式 / 文本层（顺带解决大文件闪退）

`SfPdfViewer` 会**再解析一份完整文档并栅格化页面**，大 PDF 上内存占用很高，低内存设备容易被系统杀掉。
现在：

- 超过 **40 MB** 的 PDF **默认用文本层模式**（只渲染抽出来的文字，不再加载 PDF 渲染视图）；
- 阅读页右上角可随时在「原版式 ⇄ 文本模式」之间切换，切换后自动对齐到当前朗读位置；
- 文本模式下按页拆的章（「第 N 页」）就是阅读单位，按句 / 按章 / 按页朗读都照常工作；
- 只有在原版式模式才会实例化 PDF 渲染视图，文本模式完全不碰它。

### 3. EPUB 无法解析 —— 增加兜底解析

原来的实现完全依赖 `epubx`，它遇到封面解码失败、结构不规范的书会直接抛异常，整本书就打不开。现在：

```
EPUB → epubx 解析 → 成功且抽到正文 → 返回
                  → 失败 / 结构异常 → parseEpubManually()：自己读 zip
                                      container.xml → OPF → manifest/spine → XHTML 正文
```

- 兜底路径只用 `archive` + `xml` + `html` 解压与解析，不碰封面解码，成功率高得多；
- 封面在兜底路径下**直接复制原图字节**（不解码，任何格式都不会因此失败）；
- 章节标题优先取 `<title>`，其次取 `h1`~`h4`，都没有才用「第 N 章」；
- 新增强化：正文首段若与章节标题重复（常见于 `<h1>` 与目录同名），自动去掉，避免朗读时标题读两遍。

### 4. 性能：游标换算不再每句 O(全篇)

`StructuredDocument` 的 `sentenceCount` / `paragraphCount` 改为 `late final` 惰性缓存，
并新增**每章起始句序号前缀和**：

- `indexOfCursor`：O(全篇) → O(单章)；
- `cursorAt`（通知栏拖动进度）：线性扫描 → **前缀和二分 + 章内定位**；
- 这些方法在朗读推进、通知栏进度刷新时每句都会调用，PDF 动辄上千章时差别很明显。

### 5. 本轮修掉的另一个真实问题

阅读页原先在决定 PDF 模式时，会在**主线程** `await File.length()`。除了多一次阻塞 IO，
它还会让任何依赖 fake-async 的场景直接卡住（我自己的 widget 测试就因此挂了）。
现在文件大小由 **isolate 解析时顺手量取并随结果回报**，主线程不做这次 IO。


## v1.2.1：修复 PDF 朗读 / 翻页闪退

### 根因

`SfPdfViewer` 的 `didUpdateWidget` 里有这么一段（见 syncfusion_flutter_pdfviewer 源码）：

```dart
_compareDocument(oldWidget._provider.getPdfBytes(context),
                 widget._provider.getPdfBytes(context), oldWidget.password);

Future<void> _compareDocument(Future<Uint8List> oldBytesData, Future<Uint8List> newBytesData, ...) async {
  final Uint8List oldBytes = await oldBytesData;
  final Uint8List newBytes = await newBytesData;
  if (!listEquals(oldBytes, newBytes) || ...) { await _loadPdfDocument(true, false); }
}
```

也就是说：**PDF 视图只要被 update 一次，就会把整个 PDF 文件重新读进内存并逐字节比较**。

而阅读页的 `ListenableBuilder` 监听 TtsManager，**朗读每推进一句都会重建整页**。修复前的写法是
在 `build` 里 `SfPdfViewer.file(File(path), ...)` 现场创建视图，于是：

> 每朗读一句 → 重建 → `didUpdateWidget` → 重读整个 PDF + `listEquals` 逐字节比较 + 重新生成图块

朗读 1 秒一句、300 页的 PDF 就是每秒把几十 MB 文件读一遍再逐字节比对，CPU 与内存反复冲高，
最终 OOM / 卡死被杀 → 表现为「PDF 朗读、翻页闪退」。

### 修复

| 措施 | 说明 |
| --- | --- |
| 视图只构建一次 | `late final Widget _pdfViewer = SfPdfViewer.file(...)`。Flutter 的 `updateChild` 发现 `child.widget == newWidget`（同一实例）会**直接复用并跳过 `didUpdateWidget`**，从根上消除重读 |
| 子节点槽位恒定 | Stack 里的跟随按钮改为 `SizedBox.shrink()` 占位，避免按钮出现/消失时改变 PDF 视图的槽位 |
| 跳页边界保护 | `_goToPdfPage()` 用 `pageCount` 夹取页码并 try/catch，`jumpToPage` 之前只判断 `_pdfReady`，越界页不再直接抛给视图 |
| 区分程序化跳页与用户翻页 | 新增 `_pdfTargetPage`：跳页时记录目标页，`onPageChanged` 命中目标即视为程序化跳转，不再误判成「用户翻页」而关掉跟随 |
| 控制器释放 | `PdfViewerController` 是 `ChangeNotifier`，在 `dispose()` 中释放（Flutter 先卸载子节点再调用父 State 的 dispose，因此不会出现「释放后仍被调用」） |
| 状态栏越界保护 | 底部进度文案对章号做夹取，避免极端情况下取章越界 |

### 回归测试

`test/widget_test.dart` 新增用例：用 syncfusion 现场生成 3 页 PDF → 打开阅读页 → 断言
`SfPdfViewer` 在整页重建前后是**同一个 widget 实例**（`identical(before, after)`）。
把修复改回「每次重建新建视图」后该用例会失败（`Expected: true / Actual: false`），
确认它不是空测。

- 通知栏显示书名 + 「第 x 章 · 第 y/z 页」，并提供 **上一章 / 播放暂停 / 下一章 / 停止**；
  进度条按句数映射成时间轴，**可拖动跳转**（`seek` → `TtsManager.seekToProgress`）。
- `audio_session` 配置为语音场景（正确的音频焦点与打断处理），`wakelock_plus` 在朗读期间保持 CPU 唤醒。
- `MainActivity` 改为继承 `AudioServiceActivity`；Manifest 注册 `AudioService` 与 `MediaButtonReceiver`
  （耳机 / 蓝牙媒体按键同样可用），并新增 `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限。
- 通知栏小图标为自绘白色剪影 `res/drawable/ic_stat_speech.xml`。
- 注：`wakelock_plus` 锁在 `1.2.x`——1.3+ 依赖 `package_info_plus 9.x`，其 Gradle 脚本自带 AGP 8.12 / Kotlin 2.2，
  与本工程的 AGP 8.3.2 / Kotlin 1.9.22 冲突会导致构建失败。


## v1.1.0：流畅度优化与新增功能

### 性能：大文件导入 / 打开不再卡顿或闪退

| 问题 | 处理 |
| --- | --- |
| 解析占用主线程（ANR / 闪退） | 解析整体搬到独立 `Isolate`，主线程只收进度消息；PDF 逐页抽取、EPUB 逐章解析都会回报百分比 |
| 打开大文件时无法中断 | `DocumentParseTask.cancel()` 可随时终止 isolate；退出阅读页 / 重新解析时自动取消，不残留后台任务 |
| 导入即解析导致导入卡 | 导入只登记元数据（瞬时完成），正文在打开时后台解析 |
| 超大文件内存压力 | 超过 80 MB 导入前弹确认，明确提示「后台解析、可随时返回取消」 |
| 解析进度不可见 | 阅读页显示「解析第 x/y 页 · 45%」，界面全程可交互 |

### 性能：阅读翻页卡顿

| 问题 | 处理 |
| --- | --- |
| 一章几万段时一次性构建全部段落 + 全部句子识别器（主要卡顿源） | 正文扁平化成「章节标题 + 段落」的块列表，用 `ListView.builder` 惰性构建，只构建可视区 + `cacheExtent` |
| 每个句子一个全局 `TapGestureRecognizer` 且永不释放 | 识别器改为**随段落 State 持有**，滚出屏幕即随 `dispose()` 释放；仍按 `"章:段:句"` 索引 |
| 每推进一句都重建整篇 TextSpan | 段落内缓存 `TextSpan`，只在「当前句 / 主题 / 内容」变化时重建 → 每推进一句只重排 2 个段落 |
| 高亮用 `AnimatedContainer` 造成每行都有动画层 | 改为静态 `DecoratedBox`，高亮切换不再触发布局动画 |
| 跟随滚动抖动、跳转需要多帧微调 | 目标块已构建时直接 `ensureVisible`；未构建时才「估算落点 → 按需微调」，避免逐帧位移 |

### 新增功能

- **朗读目录 / 选择页数**：阅读页右上角与底部控制栏都有「目录」。目录面板按章节展开，每章按「每页 N 段」分页（N 可在设置里选 20/40/80/120/200），可直接输入页码跳转；点击任一章 / 页即从该处开始朗读。底部状态栏实时显示「第 x 章 第 y/z 页 · 第 a 段 · 第 b 句」。
- **文档库封面**：EPUB 导入后在后台抽出封面（缩放到 400px 宽存 JPG，不阻塞导入），其它类型使用类型色渐变 + 图标占位封面；列表用 `cacheWidth` 只解码缩略图，避免大图解码掉帧。
- **浏览器收藏**：菜单「收藏本页 / 我的收藏」，收藏面板可删除、点击直达；当前页已收藏时菜单项自动变为「取消收藏本页」。
- **浏览记录**：自动记录访问（同一网址只留最新一条，上限 200 条），可查看、点击重访、一键清空。
- **自定义默认首页**：菜单「设为默认首页」，或在「设置 → 默认首页」里填写（可一键恢复默认）；首页按钮与启动页都走该配置。地址栏输入非网址内容会当作搜索词。
- **网页朗读**：菜单「朗读本页」会按 `article → main → body` 顺序抽取正文（剔除导航 / 脚本 / 样式），按段落与句子切成 ≤240 字的片段（系统 TTS 单次输入上限保护），在面板里逐段朗读并高亮跟随，可点任意段从该处开始、暂停 / 继续 / 停止。
- `TtsManager` 新增**纯文本队列朗读**（`speakLines` + `plainIndex/plainTotal`），规格要求的 `speakText` 保留为单条特例，两种模式共用同一套打断令牌与云端降级逻辑。

## 云端 TTS 配置

「设置 → 云端 TTS 配置」填入：

- Base URL：例如 `https://api.openai.com/v1`（应用会自动补 `/audio/speech`；直接填完整 `/v1/audio/speech` 也可以）
- API Key：请求头 `Authorization: Bearer <key>`

请求体为 OpenAI 兼容格式：

```json
{ "model": "tts-1", "input": "要朗读的文本", "voice": "alloy", "speed": 1.0 }
```

响应按音频二进制处理，交给 `just_audio` 播放；非 200、空响应或网络异常都会抛出，由 `TtsManager` 降级到系统引擎朗读同一段，界面会提示「已降级为系统引擎」。

## 已知边界

- PDF 文本抽取效果取决于原文件是否内嵌文本层；扫描件（纯图片 PDF）抽不到文字，会提示「没有解析到可朗读的文本」。
- TXT 会自动识别编码（UTF-8 / GBK / Big5 / UTF-16，含无 BOM 的情况）；遇到罕见的
  混合编码或 GB18030 生僻字符时仍可能有个别乱码，识别结果可在「设置 → 诊断日志」里看到
  （形如「TXT 编码：GBK」）。
- 云端 TTS 的音调参数接口本身不支持，改为在播放器侧变调（部分平台不生效）。
- **导出音频是 WAV 而不是 MP3**：本工程未内置 MP3 所需的 LAME 编码器。
- **导出音频需要 Android 11 及以上**：`flutter_tts` 在 Android 11+ 走媒体库（写入「音乐」目录），
  更早的系统写外部存储的 Music 目录，需要存储权限。
- **PDF 原版式页面上画不出句子高亮框**：`SfPdfViewer` 不暴露「PDF 坐标 → 屏幕坐标」的换算
  （没有公开的 `TransformationController`，页面缩放 / 内边距 / 滚动都是私有的），
  所以在渲染好的页面位图上无法叠加对齐的高亮。折中做法是：点播放自动切到文本模式（那里有逐句高亮），
  留在原版式时点页面任意一行从该行读起，并用顶部字幕条高亮显示当前句。
- **PDF 文字行位置最多保留 4 万行**：超大 PDF 超出后原版式的「点哪行读哪句」会失效（朗读本身不受影响）。
- **竖排（CJK vertical）没有实现**：Flutter 的文本引擎没有竖排书写模式，只能靠逐字旋转拼凑，
  效果与性能都不可接受，因此没有做。
- **网页翻译依赖 Google 翻译的可用性**：本应用只负责拼地址（`web_translate.dart`），
  翻译本身在 Google 侧完成；打不开时页面会是空白，属于网络/服务问题而非本应用缺陷。
- **复制即朗读的悬浮球只在 Android 生效**：桌面端能编译运行界面，但 `SYSTEM_ALERT_WINDOW`、
  快捷磁贴、开机自启都是 Android 独有；Dart 侧对「原生实现缺失」是静默降级（设置项显示「当前平台不支持」）。
- **开机自启不是 100% 可靠**：Android 12+ 限制后台启动前台服务，起不来时打开一次应用即可恢复
  （启动引导会补拉悬浮球）。
- 桌面端可以编译运行界面，但 `flutter_downloader`、权限申请等仅在 Android / iOS 生效。

## 关于开发方式

**本项目由 AI 开发。** 从第一行代码到单元测试、设备验证用例、文档与发布包，都由 AI 编程助手
（DeepSeek Harness 驱动的编码代理）编写；人类负责提需求、在设备上验收、决定发布。

| 角色 | 谁 |
| --- | --- |
| 写代码 / 写测试 / 写文档 / 出包 | **AI**（Dart、Kotlin、Gradle、Markdown） |
| 提需求、真机验收、决定发布 | 人类（每轮：需求 → AI 实现 → 自动化验证 → 人类确认） |

**验证到什么程度**：`flutter analyze` 零问题、**337 项单元测试**、**29 项设备测试**
（Android 14 模拟器 + 真实系统 TTS 发声链路）；每次发版都用 debug 证书出包，并做
签名（v1 + v2）/ 清单 / 冷启动 / crash 缓冲校验。

**这意味着什么**：

- 功能有自动化测试与模拟器实测背书，回归有保障（每个版本都跑全量）；
- 但**真实设备上的长测**（不同厂商 ROM、超大文件、熄屏长时间朗读、真实站点下载）
  仍建议使用者自己确认一遍；
- 发现问题欢迎开 issue：写清**复现步骤 + 设备型号 + 系统版本**，定位会快很多。
